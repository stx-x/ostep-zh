# 第 28 章　锁

<div class="chap-en">Locks</div>

<div class="chap-en">Locks</div>

在并发部分的引言里，我们已经看到并发编程中的一个根本问题：我们希望把一系列指令原子地执行，但由于单处理器上可能发生中断（或者多个处理器上多个线程在并发执行），这一点做不到。本章我们就直接正面解决这个问题，办法是引入一个称为**锁**（lock）的东西。程序员在源代码中用锁来标注，把锁放在临界区周围，从而确保这样的临界区执行起来就像一条原子指令。

## 28.1 锁：基本思想

举个例子，假设我们的临界区是这样的，也就是对共享变量最经典的更新：

`balance = balance + 1;`

当然，临界区也可以是别的形式，比如往链表里插入一个元素，或者对共享结构做更复杂的更新，不过眼下我们只保留这个简单的例子。要用锁，就在临界区前后加一些代码，像这样：

```c
lock_t mutex; // some globally-allocated lock ’mutex’
lock(&mutex);
balance = balance + 1;
unlock(&mutex);
```

锁本身就是一个变量，所以要使用锁，你必须先声明某种锁变量（比如上面的 `mutex`）。这个锁变量（以后简称“锁”）在任意时刻都保存着锁的状态。它要么是**可用**的（也叫未加锁、空闲），此时没有线程持有它；要么是**已获取**的（也叫已加锁、被持有），此时恰好有一个线程持有它，而且这个线程多半正在临界区里。我们完全可以在这种数据类型里存放别的信息，比如是哪个线程持有这把锁，或者一个用来决定获取顺序的队列，不过这类信息对锁的使用者是隐藏的。

`lock()` 和 `unlock()` 这两个例程的语义很简单。调用 `lock()` 会尝试获取锁；如果没有别的线程持有这把锁（也就是它是空闲的），调用线程就会获取到锁并进入临界区，这个线程有时被称作锁的**持有者**（owner）。如果另一个线程此时对同一个锁变量（本例中的 `mutex`）调用 `lock()`，那么在锁被别的线程持有期间，这个调用不会返回；这样一来，在第一个持锁线程待在临界区里的这段时间，其他线程就被挡在门外。

一旦锁的持有者调用 `unlock()`，锁就又变成可用的（空闲的）了。如果没有别的线程在等这把锁（也就是没有别的线程调用过 `lock()` 并卡在那里），锁的状态就直接变成空闲。如果有等待的线程（卡在 `lock()` 里），其中一个会（最终）察觉到（或被通知到）锁状态的这种变化，获取锁并进入临界区。

锁给程序员提供了对调度的一点点控制权。一般来说，我们把线程看作由程序员创建、但由操作系统以它选定的任意方式调度的实体。锁把一部分控制权交还给程序员：只要在一段代码外面套上锁，程序员就能保证这段代码里同时最多只有一个线程在活动。于是，锁帮助我们把传统操作系统调度带来的混乱，转变为一种更有秩序的活动。

## 28.2 Pthread 锁

POSIX 库给锁起的名字是**互斥锁**（mutex），因为它用来在多个线程之间提供互斥，也就是说，如果一个线程在临界区里，它就把别的线程排除在外，直到它执行完这段临界区。所以，当你看到下面这段 POSIX 线程代码时，应该明白它做的和上面的例子是一回事（这里我们再次使用了会检查加锁、解锁是否出错的包装函数）：

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
Pthread_mutex_lock(&lock); // wrapper; exits on failure
balance = balance + 1;
Pthread_mutex_unlock(&lock);
```

你可能还注意到，POSIX 版本的 `lock` 和 `unlock` 都要传入一个变量，因为我们可以用不同的锁保护不同的变量。这样做能提高并发度：与其用一把大锁，在访问任何临界区时都去抢它（一种**粗粒度**加锁策略），不如用不同的锁保护不同的数据和数据结构，从而让更多线程可以同时待在加锁的代码里（这是一种更**细粒度**的做法）。

## 28.3 构造一把锁

到这里，从程序员的角度看，你应该对锁的工作方式有了一些了解。但是我们该怎样造出一把锁呢？需要什么硬件支持？又需要什么操作系统支持？本章余下的部分就来讨论这一组问题。

要造出一把能用的锁，我们需要老朋友硬件的帮助，也需要好伙伴操作系统的帮助。多年来，各种计算机体系结构的指令集中加入了许多不同的硬件原语；我们不会去研究这些指令本身是怎样实现的（那毕竟是计算机体系结构课的内容），而是要研究如何使用它们来构造像锁这样的互斥原语。我们还会研究操作系统如何参与进来、补全整幅图景，使我们能构造出一套复杂的锁库。

## 28.4 评估锁

在动手造锁之前，我们应该先弄清目标，因此要问：如何评价某种锁实现的好坏？要判断一把锁是否可用（以及是否好用），我们应该先立几条基本标准。第一条是锁是否完成了它的基本任务，也就是提供互斥。说白了，这把锁管用吗？它能不能阻止多个线程同时进入临界区？

第二条是**公平性**。每个争用这把锁的线程，在锁空闲时是否都有公平的机会拿到它？换个角度看，就是考虑更极端的情形：有没有哪个争用的线程在等待中**饿死**，始终拿不到锁？

最后一条标准是**性能**，具体说就是使用锁带来的时间开销。这里值得考虑几种不同的情况。一种是没有争用的情况：只有一个线程运行时，它获取并释放锁的开销有多大？另一种是多个线程在单个 CPU 上争用同一把锁的情况：此时有性能问题吗？最后，在多 CPU 的机器上，每个 CPU 上的线程都来争用这把锁时，锁的表现又如何？比较这些不同的场景，我们就能更好地理解各种加锁技术的性能影响，下文会依次描述。

## 28.5 控制中断

最早用来提供互斥的方案之一，是在临界区里关中断；这个方案是为单处理器系统发明的。代码大概是这样：

```c
void lock() {
DisableInterrupts();
void unlock() {
EnableInterrupts();
```

假设我们运行在这样的单处理器系统上。在进入临界区之前关掉中断（用某种特殊的硬件指令），我们就能保证临界区里的代码不会被打断，于是它执行起来就像原子的。用完之后，我们再打开中断（同样通过硬件指令），程序就照常继续。

这种做法的主要优点是简单。你根本不用绞尽脑汁去想它为什么有效。没有中断，线程就能确信自己执行的代码会执行完，也没有别的线程会来插一脚。

不幸的是，缺点有一大堆。第一，这种做法要求我们允许任何调用线程执行特权操作（开关中断），因而必须相信这种能力不会被滥用。你早就知道，只要我们需要信任一个任意程序，多半就有麻烦。这里的麻烦有很多种表现形式：一个贪心的程序可以在开始执行时就调用 `lock()`，从而独霸处理器；更糟的是，一个出错或恶意的程序可以调用 `lock()` 之后进入死循环。后一种情况下，操作系统再也拿不回系统控制权，唯一的办法就是重启系统。把关中断当作通用的同步方案，需要应用程序太多太多的信任。

第二，这种办法在多处理器上不管用。如果多个线程运行在不同的 CPU 上，各自都想进入同一个临界区，那么关不关中断根本无所谓：线程会在别的处理器上运行，照样能进入临界区。如今多处理器已经司空见惯，所以我们的通用方案必须比这更好。

第三，长时间关中断可能导致中断丢失，进而引发严重的系统问题。举例来说，假如 CPU 错过了磁盘设备已经完成读请求这件事，操作系统怎么知道该去唤醒等待这次读操作的进程呢？

```c

void init(lock_t *mutex) {
// 0 -> lock is available, 1 -> held
mutex->flag = 0;
void lock(lock_t *mutex) {
while (mutex->flag == 1)
// TEST the flag
; // spin-wait (do nothing)
mutex->flag = 1;
// now SET it!
void unlock(lock_t *mutex) {
mutex->flag = 0;
```

正是因为这些原因，关中断只在很有限的场合被当作互斥原语使用。例如在某些情况下，操作系统自己会用关中断来保证访问自身数据结构时的原子性，或者至少避免出现某些麻烦的中断处理情形。这种用法是合理的，因为在操作系统内部，信任问题消失了——操作系统本来就一直信任自己执行特权操作。

## 28.6 一次失败的尝试：只用加载和存储

要走出基于中断的做法，我们就得依靠 CPU 硬件以及它提供的指令来构造一把像样的锁。先让我们试着用一个简单的标志变量来造锁。在这次失败的尝试中，我们能看到构造锁所需的一些基本思路，并且（但愿）能看清为什么只用一个变量、通过普通的加载和存储去访问它是不够的。

在第一次尝试里（图 28.1），想法很简单：用一个简单的变量（`flag`）来表示是否有某个线程占着锁。第一个进入临界区的线程会调用 `lock()`，它检查 `flag` 是否等于 1（此时不是），然后把 `flag` 置为 1，表示该线程现在持有锁。临界区执行完后，线程调用 `unlock()` 清掉 `flag`，表示锁不再被持有。

如果另一个线程在第一个线程待在临界区期间调用 `lock()`，它就会在 `while` 循环里**自旋等待**（spin-wait），直到那个线程调用 `unlock()` 清掉 `flag` 为止。第一个线程一旦这么做，等待的线程就会跳出 `while` 循环，把 `flag` 置为 1 归自己所有，然后进入临界区。

不幸的是，这段代码有两个问题：一个是正确性，另一个是性能。只要习惯了并发编程的思维方式，正确性问题很容易看出来。设想图 28.2 中的代码交错执行，并假设开始时 `flag=0`。

从这段交错执行中可以看到，只要中断来得“巧”（或者说来得不巧），我们就能轻易造出两个线程都把 `flag` 置为 1、于是两个线程都能进入临界区的情形。这种行为被专业人士称为“糟糕”——我们显然没能提供最基本的要求：互斥。

性能问题我们稍后会更多讨论，它指的是线程等待一把已被持有的锁的方式：它无休止地检查 `flag` 的值，这种技术称为自旋等待。自旋等待在等待别的线程释放锁时白白浪费时间。在单处理器上，这种浪费格外严重，因为等待者所等的那个线程甚至根本没法运行（至少在下一次上下文切换之前是这样）！所以，在我们继续前进、开发更精巧的方案时，也应该考虑如何避免这类浪费。

## 28.7 用测试并设置构造可用的自旋锁

因为关中断在多处理器上行不通，而用加载和存储的简单做法（如上所示）也不行，系统设计者开始为加锁发明硬件支持。最早的多处理器系统，比如 20 世纪 60 年代初的 Burroughs B5000 [M82]，就有这样的支持；如今所有系统都提供这类支持，哪怕是单 CPU 系统。

最容易理解的一种硬件支持叫作**测试并设置**（test-and-set，也叫原子交换¹）指令。我们用下面这段 C 代码来定义测试并设置指令的行为：

```c
int TestAndSet(int *old_ptr, int new) {
int old = *old_ptr; // fetch old value at old_ptr
*old_ptr = new;
// store ’new’ into old_ptr
return old;
// return the old value
```

测试并设置指令做的事是这样的：它返回 `old_ptr` 所指的旧值，同时把这个值更新为 `new`。关键当然在于，这一系列操作是原子地完成的。它之所以叫“测试并设置”，是因为它让你在“设置”内存单元为新值的同时“测试”旧值（也就是被返回的值）；事实证明，这条稍微强大一点的指令就足以造出一把简单的自旋锁，我们现在就在图 28.3 中考察这一点。或者更好：你先自己把它想出来！

让我们确认一下为什么这把锁能工作。先设想一个线程调用 `lock()` 而当前没有别的线程持有锁的情形，此时 `flag` 应该是 0。当线程调用 `TestAndSet(flag, 1)` 时，该例程会返回 `flag` 的旧值，也就是 0；于是调用线程（它正在测试 `flag` 的值）不会在 `while` 循环里被困住自旋，而是获取到锁。同时，线程会原子地把值设为 1，表示锁现在被持有了。当线程执行完临界区，它调用 `unlock()` 把 `flag` 设回 0。

我们可以设想的第二种情形，是某个线程已经持有锁（即 `flag` 为 1）。这时该线程也会调用 `lock()`，进而调用 `TestAndSet(flag, 1)`。这一次，`TestAndSet()` 会返回 `flag` 处的旧值，也就是 1（因为锁被持有），同时再次把它设为 1。只要锁还被别的线程持有，`TestAndSet()` 就会反复返回 1，于是这个线程就一直自旋，直到锁最终被释放。当 `flag` 终于被别的线程设为 0 之后，这个线程再次调用 `TestAndSet()`，这次会返回 0 并原子地把值设为 1，于是它获取到锁，进入临界区。

把（对旧锁值的）测试与（对新值的）设置合并为一个原子操作，我们就保证了只有一个线程能获得锁。这就是构造一个可用的互斥原语的方法！

::: tip 把并发想象成一个恶意的调度器
从这个例子中，你或许能体会到理解并发执行所需采取的方法。你应该试着假装自己是一个恶意的调度器，专门在最不合适的时刻打断线程，以挫败它们构造同步原语的拙劣尝试。你这个调度器可真坏！虽然中断的确切时序也许不太可能发生，但它确实可能发生，而这就足以说明某种做法行不通了。带着恶意去思考是有用的！（至少有时候有用。）
:::

你现在可能也明白了，为什么这类锁通常被称为**自旋锁**（spin lock）。它是最容易构造的一类锁，只是自旋，用 CPU 周期换取锁变为可用。要在单处理器上正确工作，它需要**抢占式**调度器（也就是会不时通过定时器中断某个线程，以便运行另一个线程的那种调度器）。没有抢占，自旋锁在单 CPU 上没多大意义，因为在 CPU 上自旋的线程永远不会主动让出它。

## 28.8 评估自旋锁

有了基本的自旋锁，我们现在就可以按照前面描述的几个维度来评估它的效果。锁最重要的方面是正确性：它提供互斥吗？这里的答案是肯定的：自旋锁一次只允许一个线程进入临界区。所以，我们有一把正确的锁。

下一个维度是公平性。自旋锁对等待的线程有多公平？你能保证某个等待的线程最终进入临界区吗？很遗憾，这里的答案是个坏消息：自旋锁不提供任何公平性保证。事实上，在争用的情况下，一个自旋的线程可能会永远自旋下去。简单的自旋锁（如目前所讨论的）不公平，可能导致**饥饿**。

最后一个维度是性能。使用自旋锁的代价是什么？为了更仔细地分析，我们建议考虑几种不同的情况。第一种，设想线程在单个处理器上争用锁；第二种，考虑线程分布在许多 CPU 上的情形。

对自旋锁来说，在单 CPU 的情况下，性能开销可能相当难受；设想持锁的线程在临界区内被抢占了。调度器随后可能会把其他每个线程都运行一遍（设想还有 N − 1 个），而它们每一个都试图获取锁。这种情况下，这些线程中的每一个都会自旋一整个时间片才放弃 CPU，白白浪费 CPU 周期。

不过在多 CPU 上，自旋锁工作得相当不错（如果线程数大致等于 CPU 数）。思路是这样的：设想 CPU 1 上的线程 A 和 CPU 2 上的线程 B 都在争用一把锁。如果线程 A（CPU 1）先拿到锁，然后线程 B 尝试获取，B 就会（在 CPU 2 上）自旋。然而，临界区想必很短，所以锁很快变为可用，并被线程 B 获取。在这种情况下，自旋等待另一处理器上持有的锁不会浪费多少周期，因此可能是有效的。

`lock()` 这段代码是唯一有意思的部分。首先，线程自旋等待 `flag` 被置为 0（表示锁未被持有）。一旦如此，线程就通过条件存储尝试获取锁；如果成功，线程已经原子地把 `flag` 的值改为 1，于是可以进入临界区。

注意条件存储的失败是怎么发生的。一个线程调用 `lock()` 并执行链接加载，因为锁未被持有而返回 0。在它来得及尝试条件存储之前，它被中断了，另一个线程进入锁的代码，也执行了链接加载指令，同样得到 0 并继续执行。此时，两个线程都已执行过链接加载，各自都即将尝试条件存储。这些指令的关键特性是：只有其中一个线程能成功地把 `flag` 更新为 1，从而获取锁；第二个尝试条件存储的线程会失败（因为另一个线程在它的链接加载和条件存储之间更新了 `flag` 的值），于是不得不重新尝试获取锁。

```c
void lock(lock_t *lock) {
while (LoadLinked(&lock->flag) ||
!StoreConditional(&lock->flag, 1))
; // spin
```

注意这个方案与我们此前几次尝试的一个重要区别：它保证所有线程都能向前推进。一个线程一旦分到自己的票号，它将来总会在某个时刻被调度到（等它前面的那些线程穿过临界区、释放锁之后）。在我们之前的尝试中，没有这种保证；例如一个在测试并设置上自旋的线程，即便其他线程反复获取和释放锁，它也可能永远自旋下去。

## 28.12 自旋太多怎么办？

我们基于硬件的锁很简单（只有几行代码），而且管用（你甚至可以写点代码去证明这一点），这是任何系统或代码的两个优秀品质。然而在某些情况下，这些方案可能相当低效。设想你在单个处理器上运行两个线程。再设想其中一个线程（线程 0）正在临界区里，因而持有一把锁，而不幸被中断了。第二个线程（线程 1）现在试图获取锁，却发现它被持有，于是开始自旋。自旋，再自旋，继续自旋。最后定时器中断响了，线程 0 又被运行，释放了锁，最终（比如说下次它运行时）线程 1 就不必自旋那么久，能够获取到锁了。所以，只要线程在这种情形下陷入自旋，它就浪费掉一整个时间片，什么也不做，只是检查一个根本不会改变的值！当 N 个线程争用一把锁时，问题更糟：可能有 N − 1 个时间片被以类似的方式浪费掉，只是自旋等待某一个线程释放锁。于是，我们的下一个问题就是：

::: crux 如何避免自旋
怎样才能构造出一把不必在 CPU 上无谓自旋浪费时间的锁？
:::

光靠硬件支持解决不了这个问题。我们还需要操作系统的支持！现在来看看这究竟可以怎么做。

## 28.13 一个简单的办法：干脆让出 CPU

硬件支持已经把我们带得相当远了：可用的锁，甚至（像票据锁那样）获取锁的公平性。但我们仍然有个问题：当临界区里发生上下文切换，线程开始无休止地自旋、等待被中断的（持锁）线程再次被运行时，该怎么办？

我们的第一次尝试是一个简单而友好的办法：既然要自旋，不如把 CPU 让给别的线程。正如 Al Davis 可能会说的：“让出 CPU 吧，宝贝！”[D91] 图 28.8 展示了这种做法。

<img src="/figures/28-f05.png" alt="Figure 28.8" loading="lazy">
<figcaption><span class="fig-label">图 28.8</span>带测试并设置和 yield 的锁</figcaption>

在这种做法中，我们假设有一个操作系统原语 `yield()`，线程想放弃 CPU、让另一个线程运行时可以调用它。一个线程可以处于三种状态之一（运行、就绪或阻塞）；`yield` 只是一个系统调用，它把调用者从运行态移到就绪态，从而让另一个线程转入运行态。也就是说，让出的线程实际上把自己取消了调度。

想想一个 CPU 上两个线程的例子；这种情况下，我们基于 yield 的做法相当好用。如果一个线程碰巧调用 `lock()` 并发现锁被持有，它就干脆让出 CPU，于是另一个线程得以运行并执行完它的临界区。在这个简单的场景里，让步的做法效果很好。

现在让我们考虑有许多线程（比如 100 个）反复争用一把锁的情形。这时，如果一个线程获取到锁并在释放前被抢占，其他 99 个线程都会调用 `lock()`、发现锁被持有，然后让出 CPU。假设是某种轮转调度器，这 99 个线程中的每一个都会在持锁线程再次得到运行之前，把这个“运行—让出”的模式走一遍。这虽然比我们自旋的做法好（后者会浪费 99 个时间片去自旋），但代价仍然不小；上下文切换的开销可能相当可观，因此浪费依然很多。

更糟的是，这个办法没有解决饥饿问题。一个线程可能陷入无休止的 yield 循环，而其他线程反复进出临界区。我们显然需要一个直接解决饥饿问题的方案。

## 28.14 用队列：睡眠代替自旋

前面某些做法（票据锁除外）的真正问题在于，它们把太多事情交给了运气。是调度器决定下一个运行哪个线程；如果调度器做了糟糕的选择，那么被运行的线程要么必须自旋等待锁（我们的第一种做法），要么立刻让出 CPU（我们的第二种做法）。无论哪种，都可能浪费，而且都无法防止饥饿。

```c
typedef struct __lock_t {
int flag;
int guard;
queue_t *q;
} lock_t;
void lock_init(lock_t *m) {
m->flag
m->guard = 0;
queue_init(m->q);
void lock(lock_t *m) {
while (TestAndSet(&m->guard, 1) == 1)
; //acquire guard lock by spinning
if (m->flag == 0) {
m->flag = 1; // lock is acquired
m->guard = 0;
} else {
queue_add(m->q, gettid());
m->guard = 0;
park();
void unlock(lock_t *m) {
while (TestAndSet(&m->guard, 1) == 1)
; //acquire guard lock by spinning
if (queue_empty(m->q))
m->flag = 0; // let go of lock; no one wants it
unpark(queue_remove(m->q)); // hold lock
// (for next thread!)
m->guard = 0;
```

因此，我们必须显式地对“当前持有者释放锁之后由哪个线程获取”施加一些控制。要做到这一点，我们需要操作系统再多给一点支持，还需要一个队列来记录哪些线程正在等待获取锁。

为简单起见，我们使用 Solaris 提供的支持，也就是两个调用：`park()` 让调用线程睡眠，`unpark(threadID)` 唤醒由 `threadID` 指定的某个线程。这两个例程可以配合使用来构造一把锁：当调用者试图获取一把被持有的锁时让它睡眠，锁空出来时再把它唤醒。我们来看图 28.9 中的代码，理解一下这类原语的一种可能用法。

::: aside 又一个避免自旋的理由：优先级反转
避免自旋锁的一个好理由是性能：正如正文所述，如果一个线程在持锁期间被中断，其他使用自旋锁的线程就会把大量 CPU 时间花在等待锁变为可用上。不过，在某些系统上，避免自旋锁还有另一个有趣的理由：正确性。值得警惕的问题叫作**优先级反转**（priority inversion），不幸的是，这是一场星际灾难，地球上 [M15] 和火星上 [R97] 都发生过！假设系统里有两个线程。线程 2（T2）的调度优先级高，线程 1（T1）的优先级低。在这个例子里，假设只要两者都可运行，CPU 调度器总是运行 T2 而不运行 T1；只有当 T2 无法运行时（比如 T2 阻塞在 I/O 上），T1 才会运行。现在问题来了。假设 T2 因某种原因被阻塞。于是 T1 运行，抢到一把自旋锁，进入临界区。此时 T2 解除阻塞（也许因为某个 I/O 完成了），CPU 调度器立刻调度它（于是 T1 被取消调度）。T2 现在试图获取锁，但拿不到（T1 持有锁），于是它就一直自旋。因为这是自旋锁，T2 会永远自旋下去，系统就挂死了。遗憾的是，仅仅避免使用自旋锁并不能避免反转问题。设想三个线程 T1、T2、T3，T3 优先级最高，T1 最低。现在设想 T1 抢到一把锁。接着 T3 开始运行，由于它优先级比 T1 高，会立即运行（抢占 T1）。T3 试图获取 T1 持有的锁，却只能卡在那里等，因为 T1 还持有它。如果这时 T2 开始运行，它的优先级比 T1 高，因此它会运行。而优先级比 T2 高的 T3，却卡在等待 T1，而 T1 在 T2 运行的情况下可能永远得不到运行机会。强大的 T3 跑不了，卑微的 T2 却控制着 CPU，这难道不悲哀吗？高优先级也不复当年的威风了。你可以通过……来解决这个问题。
:::

在这个例子里，我们做了几件有意思的事。第一，我们把老的测试并设置思路与一个显式的锁等待者队列结合起来，造出一把更高效的锁。第二，我们用队列来帮助控制下一个谁拿到锁，从而避免饥饿。

你可能注意到 `guard` 是怎么用的（图 28.9）：它基本上就是一把自旋锁，保护着锁内部对 `flag` 和队列的操作。所以这种做法并没有完全避免自旋等待；一个线程在获取或释放锁的过程中可能被中断，从而让别的线程自旋等待它再次运行。不过，自旋的时间相当有限（只是 `lock` 和 `unlock` 代码里的几条指令，而不是用户定义的临界区），因此这种做法可能还算合理。

你可能还观察到，在 `lock()` 中，当线程无法获取锁（锁已被持有）时，我们会小心地把自己加入队列（调用 `gettid()` 函数取得当前线程的 ID），把 `guard` 置为 0，然后让出 CPU。留给读者的一个问题：如果 `guard` 锁的释放放在 `park()` 之后而不是之前，会发生什么？提示：会有坏事发生。

你可能还会发现，当另一个线程被唤醒时，`flag` 并没有被设回 0。为什么呢？这并非错误，而是必需的！当一个线程被唤醒时，它的处境就像是从 `park()` 返回；然而在代码的那个位置它并不持有 `guard`，因此根本无法尝试把 `flag` 设为 1。于是，我们直接把锁从释放它的线程手里交给下一个获取它的线程；`flag` 在这中间不会被设为 0。

最后，你可能注意到这个解法里在调用 `park()` 之前存在一个看似明显的竞态条件。只要时序稍有偏差，一个线程就会即将 park，因为它认为自己应该睡到锁不再被持有为止。而此刻若切换到另一个线程（比如持锁线程），就可能带来麻烦，例如那个线程随后释放了锁。那么第一个线程接下来的 park 就（可能）会永远睡下去，这个问题有时被称为**唤醒/等待竞态**（wakeup/waiting race）。

Solaris 通过增加第三个系统调用 `setpark()` 来解决这个问题。调用这个例程，线程可以表明自己即将 park。如果它随后恰巧被中断，而另一个线程在 `park` 真正被调用之前调用了 `unpark`，那么接下来的 `park` 会立即返回，而不是睡下去。`lock()` 内部的代码改动非常小：

```c
queue_add(m->q, gettid());
setpark(); // new code
m->guard = 0;
```

另一种解法是把 `guard` 传进内核。那样的话，内核可以采取预防措施，原子地释放锁并把正在运行的线程出队。

## 28.15 不同的操作系统，不同的支持

## 28.16 两阶段锁

最后一点：Linux 这种做法带着一种古老方案的影子，这种方案多年来时兴时废，至少可以追溯到 20 世纪 60 年代初的 Dahm 锁 [M82]，如今被称为**两阶段锁**（two-phase lock）。两阶段锁认识到自旋可能有用，尤其是在锁即将被释放的时候。于是在第一阶段，锁先自旋一会儿，指望能拿到锁。

然而，如果在第一个自旋阶段没能获取到锁，就进入第二阶段：调用者被置为睡眠，只在锁稍后变为空闲时才被唤醒。上面的 Linux 锁就是这样一种锁，只不过它只自旋一次；推广一下，可以在一段时间内循环自旋，然后再使用 futex 支持去睡眠。

两阶段锁又是一个混合式方案实例：把两个好主意结合起来，或许真能得到一个更好的。当然，是否真的更好，很大程度上取决于许多因素，包括硬件环境、线程数量以及其他负载细节。一如既往，要造出一把适用于所有可能场景的通用锁，是相当有挑战性的。

## 28.17 小结

上面的做法展示了如今真实世界的锁是怎样构造的：一些硬件支持（体现为一条更强大的指令）加上一些操作系统支持（例如 Solaris 上的 `park()` 和 `unpark()` 原语，或者 Linux 上的 futex）。当然，细节各有不同，执行这种加锁的确切代码通常经过高度调优。如果想了解更多细节，可以去翻翻 Solaris 或 Linux 的代码库，读起来很有意思 [L09, S09]。关于现代多处理器上各种加锁策略的比较，另见 David 等人出色的工作 [D+13]。

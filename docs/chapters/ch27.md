## 27.1 线程创建

写多线程程序，第一件必须会做的事就是创建新线程，因此总要存在某种线程创建接口。在 POSIX 中，这很简单：

```c
#include <pthread.h>
pthread_create(pthread_t
*thread,
const pthread_attr_t *attr,
*(*start_routine)(void*),
*arg);
```

这个声明看起来有点复杂（如果你没用过 C 的函数指针，尤其如此），其实并不算糟。它有四个参数：`thread`、`attr`、`start_routine` 和 `arg`。第一个参数 `thread` 是指向 `pthread_t` 结构的指针；我们通过这个结构与线程打交道，因此需要把它传给 `pthread_create()` 以便完成初始化。

第二个参数 `attr` 用于指定这个线程可能具有的属性，例如设置栈大小，或者指定线程调度优先级方面的信息。属性要用单独的 `pthread_attr_init()` 调用来初始化，细节见手册页。不过大多数情况下用默认值就够了，所以这里直接传 `NULL` 进去。

第三个参数最复杂，但它要回答的问题其实只是：这个线程应该从哪个函数开始运行？在 C 里我们把这叫做函数指针，它的含义是：这里需要一个函数名（`start_routine`），该函数接受一个 `void *` 类型的参数（见 `start_routine` 后面的括号），并返回一个 `void *` 类型的值（也就是 void 指针）。

如果这个例程需要的是整数参数而不是 void 指针，声明就变成这样：

```c
int pthread_create(..., // first two args are the same
void *(*start_routine)(int),
```

如果例程接受的是 void 指针参数、但返回整数，那么声明就是这样：

```c
int pthread_create(..., // first two args are the same
int (*start_routine)(void *),
void *arg);
```

最后，第四个参数 `arg` 正是要传给线程入口函数的那个参数。你可能会问：为什么需要这些 void 指针？答案很简单：把 `void *` 作为入口函数的参数，我们就能传入任意类型的参数；把它作为返回值，线程就能返回任意类型的结果。

来看图 27.1 的例子。这里创建了一个线程，并向它传入两个参数，这两个参数被打包进我们自己定义的 `myarg_t` 类型。线程创建之后，只要把参数强制转换回它期望的类型，就能按需解包出各个参数。

就是这样！一旦创建了线程，你就真的多了一个活生生的执行实体：它拥有自己的调用栈，并与程序中所有已存在的线程运行在同一个地址空间里。好戏就此开场！

## 27.2 线程完成

上面的例子演示了如何创建线程。可是，如果你想等一个线程结束呢？这需要专门做点事情：必须调用 `pthread_join()`。

```c
int pthread_join(pthread_t thread, void **value_ptr);
```

这个例程接受两个参数。第一个是 `pthread_t` 类型，用来指定要等待哪个线程。这个变量由线程创建例程初始化（也就是你把指向它的指针作为参数传给 `pthread_create()` 的时候）；只要把它保存下来，之后就能用它等待那个线程终止。

第二个参数是指向你期望取回的返回值的指针。由于例程可以返回任何东西，它被定义为返回 void 指针；又因为 `pthread_join()` 会改变传入参数的值，所以你要传的是那个值的指针，而不只是值本身。

再看一个例子（图 27.2）。代码中又一次创建了单个线程，并通过 `myarg_t` 结构传入几个参数。返回值使用 `myret_t` 类型。线程运行结束后，一直等在 `pthread_join()` 里的主线程随即返回，于是我们就能访问线程返回的值，也就是 `myret_t` 里的内容。

关于这个例子有几点要注意。首先，很多时候我们并不需要做这套痛苦的参数打包与解包。比如创建一个不带参数的线程时，创建时直接传入 `NULL` 即可。同样，如果不关心返回值，也可以给 `pthread_join()` 传 `NULL`。

```c
typedef struct { int a; int b; } myarg_t;
typedef struct { int x; int y; } myret_t;
void *mythread(void *arg) {
myret_t *rvals = Malloc(sizeof(myret_t));
rvals->x = 1;
rvals->y = 2;
return (void *) rvals;
int main(int argc, char *argv[]) {
pthread_t p;
myret_t *rvals;
myarg_t args = { 10, 20 };
Pthread_create(&p, NULL, mythread, &args);
Pthread_join(p, (void **) &rvals);
printf("returned %d %d\n", rvals->x, rvals->y);
free(rvals);
return 0;
```

其次，如果只传一个值（比如一个 `long long int`），也不必把它包装成参数。图 27.3 给出了例子。这种情况下日子稍微好过一点，因为我们不用把参数和返回值塞进结构体里。

第三，要特别小心线程如何返回数值。具体来说，绝不要返回指向线程调用栈上分配的内存的指针。如果真的这么做，你猜会发生什么？（想一想！）下面这段危险代码改编自图 27.2 的例子。

```c
void *mythread(void *arg) {
myarg_t *args = (myarg_t *) arg;
printf("%d %d\n", args->a, args->b);
myret_t oops; // ALLOCATED ON STACK: BAD!
oops.x = 1;
oops.y = 2;
return (void *) &oops;
```

在这段代码里，变量 `oops` 分配在 `mythread` 的栈上。函数返回时，它会被自动释放（栈之所以这么好用，正是因为这个！），因此把指向一个已被释放的变量的指针返回出去，会带来各种各样糟糕的后果。当你打印自以为返回的值时，多半（但不一定！）会大吃一惊。不妨自己动手试试看！

最后，你可能会注意到：用 `pthread_create()` 创建线程、紧接着立刻调用 `pthread_join()`，这种创建线程的方式挺奇怪。事实上，要完成同样的事情有个更简单的办法，叫做过程调用（procedure call）。显然，我们通常不会只创建一个线程然后等它结束，否则用线程就没什么意义了。

还应注意，并非所有多线程代码都会用到 join。例如，一个多线程 Web 服务器可能创建一批工作线程，然后让主线程无限循环地接受请求并把它们交给工作线程。这类长期运行的程序或许根本不需要 join。但并行程序如果创建线程是为了（并行地）完成某项特定任务，那就多半会用 join 来确保所有工作都已完成，才退出或进入下一个计算阶段。

## 27.3 锁

除了线程创建和 join，POSIX 线程库提供的下一组最有用的函数，大概就是用锁为临界区提供互斥的那些函数了。为此最基本的一对例程如下：

```c
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
```

这两个例程应该不难理解和使用。当你的代码中有一段临界区、需要加以保护才能正确运行时，锁就很有用。你大概能想象出代码的样子：

```c
pthread_mutex_t lock;
pthread_mutex_lock(&lock);
x = x + 1; // or whatever your critical section is
pthread_mutex_unlock(&lock);
```

这段代码的意图如下：调用 `pthread_mutex_lock()` 时，如果没有其他线程持有锁，该线程就获得锁并进入临界区。如果确实有别的线程持有锁，试图获取锁的线程就不会从调用中返回，直到它把锁拿到手（这意味着持锁线程已经通过 unlock 释放了锁）。当然，某一时刻可能有许多线程卡在锁获取函数里等待；但只有真正拿到锁的那个线程才应该调用 unlock。

遗憾的是，这段代码在两个重要方面是有问题的。第一个问题是缺少正确的初始化。所有锁都必须正确初始化，才能保证一开始就具有正确的值，从而在调用 lock 和 unlock 时按预期工作。

在 POSIX 线程中，初始化锁有两种办法。一种是用 `PTHREAD_MUTEX_INITIALIZER`，如下所示：

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
```

这样做会把锁设成默认值，使锁可以使用。动态的方式（即在运行时）则是调用 `pthread_mutex_init()`，如下所示：

```c
int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0); // always check success!
```

这个例程的第一个参数是锁本身的地址，第二个参数是一组可选属性。属性细节请自行查阅；传 `NULL` 就是使用默认值。两种方式都能用，但我们通常采用动态（后一种）方式。注意，用完锁之后还应当相应调用 `pthread_mutex_destroy()`，细节见手册页。

上面那段代码的第二个问题，是调用 lock 和 unlock 时没有检查错误码。和你在 UNIX 系统上几乎调用的任何库例程一样，这些例程也可能失败！如果代码没有正确检查错误码，失败就会悄无声息地发生——在这个例子里，这可能就意味着多个线程同时进入了临界区。最起码要用包装函数断言调用成功，如图 27.4 所示；更复杂的（非玩具级）程序不能一出错就退出，应当检查失败，并在调用不成功时采取合适的处理。

```c
// Keeps code clean; only use if exit() OK upon failure
void Pthread_mutex_lock(pthread_mutex_t *mutex) {
int rc = pthread_mutex_lock(mutex);
assert(rc == 0);
```

<div class="code-cap"><span class="code-label">图 27.4</span>一个包装函数的示例</div>

lock 和 unlock 并不是 pthreads 库中仅有的与锁打交道的例程。还有两个值得关注的例程：

```c
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_timedlock(pthread_mutex_t *mutex,
struct timespec *abs_timeout);
```

这两个调用都用于获取锁。trylock 版本在锁已被持有时会返回失败；timedlock 版本则在超时之后或者拿到锁之后返回，以先发生者为准。因此，超时为零的 timedlock 就退化成了 trylock。这两个版本一般都应避免使用；不过在少数情形下，避免在锁获取例程里（可能无限期地）卡住是有用的，后面的章节（例如研究死锁时）我们还会看到。

## 27.4 条件变量

任何线程库的另一大组成部分，POSIX 线程自然也不例外，就是条件变量。当线程之间必须进行某种信号通知时——一个线程在继续之前要等另一个线程做某件事——条件变量就派上了用场。希望以这种方式交互的程序会用到两个主要例程：

```c
int pthread_cond_wait(pthread_cond_t *cond,
pthread_mutex_t *mutex);
int pthread_cond_signal(pthread_cond_t *cond);
```

要使用条件变量，还必须额外有一把与之关联的锁。调用上述任一例程时，都应该持有这把锁。

第一个例程 `pthread_cond_wait()` 会让调用线程睡眠，从而等待其他线程给它发信号——通常是在程序中某些状态发生了变化、而这个正在睡觉的线程可能会关心的时候。典型用法如下：

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

Pthread_mutex_lock(&lock);
while (ready == 0)
Pthread_cond_wait(&cond, &lock);
Pthread_mutex_unlock(&lock);
```

这段代码在初始化相关的锁和条件变量之后，检查变量 `ready` 是否已被设为非零值。如果还没有，线程就调用 wait 例程睡过去，直到其他线程把它唤醒。

唤醒线程的代码（会运行在另一个线程里）大致如下：

```c
Pthread_mutex_lock(&lock);
ready = 1;
Pthread_cond_signal(&cond);
Pthread_mutex_unlock(&lock);
```

关于这段代码，有几点值得注意。第一，发信号时（以及修改全局变量 `ready` 时），我们始终确保持有锁。这样就不会不小心在代码中引入竞态条件。

第二，你可能注意到 wait 调用把锁作为第二个参数，而 signal 调用只接受一个条件变量。之所以有这种差别，是因为 wait 除了让调用线程睡眠之外，还会在让调用者入睡时释放这把锁。设想如果它不释放：另一个线程怎么可能拿到锁、并向它发出唤醒信号呢？而在被唤醒返回之前，`pthread_cond_wait()` 会重新获取锁，从而保证等待线程在等待序列开头获取锁、到结尾释放锁之间的任何时刻，都持有这把锁。

最后还有一个古怪之处：等待线程用 while 循环而不是简单的 if 语句来重新检查条件。我们会在后面专门讲条件变量的一章里详细讨论这个问题，但一般来说，用 while 循环是既简单又安全的做法。虽然它要重新检查条件（可能带来一点额外开销），但某些 pthread 实现可能会虚假唤醒等待线程；在这种情况下，如果不重新检查，等待线程就会继续以为条件已经改变，其实并没有。所以，把"被唤醒"看成"某件事可能变了"的提示，而不是板上钉钉的事实，会更稳妥。

注意，有时人们很想用简单的标志位在线程之间传递信号，而不用条件变量加配套的锁。例如可以把上面的等待代码改写成这样：

```c
while (ready == 0)
; // spin
```

相应的发信号代码则只是：`ready = 1;`

千万别这么干，原因如下。第一，它在很多情况下性能很差（长时间自旋白白浪费 CPU 周期）。第二，它容易出错。正如近期研究所显示的 [X+10]，用上面这种标志位在线程之间做同步时，犯错误出奇地容易；在那项研究中，这类"临时凑合"式同步大约有一半是有 bug 的！别偷懒，即使你觉得不用条件变量也能蒙混过关，也请用条件变量。

如果条件变量听起来让人困惑，暂时不用太担心——我们会在后续章节里非常详细地讲解它们。在那之前，只要知道它们存在，并对它们的用途和用法有个大致印象，就足够了。

## 27.5 编译与运行

本章所有代码示例都比较容易跑起来。编译时必须在代码中包含头文件 `pthread.h`。在链接命令行上，还必须显式地与 pthreads 库链接，即加上 `-pthread` 标志。

例如，编译一个简单的多线程程序，你只需这样做：

```c
prompt> gcc -o main main.c -Wall -pthread
```

只要 `main.c` 包含了 pthreads 头文件，你就成功编译出了一个并发程序。至于它能不能正常工作，一如往常，那完全是另一回事。

## 27.6 小结

我们介绍了 pthread 库的基础知识，包括线程创建、用锁构建互斥，以及用条件变量进行信号通知和等待。要写出健壮高效的多线程代码，除此之外你并不需要太多东西——只需要耐心和十二分的谨慎！

本章最后给出一组提示，它们或许对编写多线程代码有所帮助（详见下页的边注）。API 中还有其他有趣的方面；如果想了解更多，在 Linux 系统上输入 `man -k pthread`，就能看到构成整个接口的一百多个 API。不过，本文讨论的基础内容应该足以让你构建复杂的（也希望是正确的、高效的）多线程程序。线程的难点不在 API，而在于你构建并发程序时那些棘手的逻辑。继续读下去吧。

::: aside 线程 API 使用准则

使用 POSIX 线程库（其实任何线程库都一样）构建多线程程序时，有一些细小但重要的地方要记住：

- **保持简单。** 最重要的是，线程之间任何加锁或发信号的代码都应尽可能简单。复杂的线程交互必然带来 bug。
- **尽量减少线程交互。** 尽量把线程相互作用的途径数量降到最低。每一种交互都应仔细考虑，并用久经考验的成熟方法来构造（其中许多方法我们将在后续章节中学到）。
- **初始化锁和条件变量。** 不这么做，代码就会时好时坏，而且失败得莫名其妙。
- **检查返回值。** 当然，你写的任何 C 和 UNIX 程序都应该检查每一个返回值，这里也一样。不检查会导致古怪而难以理解的行为，让你很可能 (a) 尖叫，(b) 揪掉一些头发，或者 (c) 两者都来。
- **小心向线程传参、从线程返回值。** 特别是，只要你在传递指向栈上分配变量的引用，你多半就是在做错事。
- **每个线程都有自己的栈。** 与上一点相关，请记住每个线程都有自己的栈。因此，如果某个线程正在执行的某个函数里有局部变量，它实质上是该线程私有的，其他线程无法（轻易）访问。要在多个线程之间共享数据，值必须放在堆上，或者放在其他全局可访问的位置。
- **线程之间发信号一定要用条件变量。** 用简单的标志位往往很诱人，但不要这么做。
- **善用手册页。** 特别是在 Linux 上，pthread 的手册页信息量很大，讨论了许多这里的细微之处，而且往往更加详细。仔细读！

:::

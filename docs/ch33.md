# 第 33 章　基于事件的并发

<div class="chap-en">Event-based Concurrency (Advanced)</div>

到目前为止，我们讨论并发时都假定：构建并发应用只有用线程这一条路。就像生活中的许多事情一样，这话并不完全对。具体来说，还有另一种并发编程风格，常常用于基于 GUI 的应用 [O96]，也用于某些类型的互联网服务器 [PDZ99]。这种风格称为**基于事件的并发**（event-based concurrency），在一些现代系统中流行起来，包括 node.js [N13] 这样的服务端框架；但它的根在 C/UNIX 系统里，下面我们就来讨论。

基于事件的并发要解决的问题有两层。第一，在多线程应用中正确地管理并发可能相当困难；如前所述，漏加锁、死锁以及其他各种棘手的毛病都可能冒出来。第二，在多线程应用里，开发者对某一时刻究竟调度了什么几乎没有控制权：程序员只是创建线程，然后指望底层操作系统在可用的 CPU 上以合理的方式调度它们。要构建一个通用、对所有工作负载在任何情况下都表现良好的调度器实在太难，因此操作系统有时会以不那么理想的方式调度工作。于是，就有了……

::: crux 如何在不使用线程的情况下构建并发服务器

能不能不用线程来构建并发服务器，从而既把并发的控制权握在手里，又避开那些似乎总在折磨多线程应用的问题？

:::

## 33.1 基本思路：事件循环

如上所述，我们将采用的基本方法叫作基于事件的并发。这个思路相当简单：你只是等待某件事（也就是一个“事件”）发生；当它发生时，你判断它是什么类型的事件，然后完成它所需的那点工作（这可能包括发出 I/O 请求，或把其他事件安排到以后再处理，等等）。就这样！

在深入细节之前，先看看一个典型的基于事件的服务器长什么样。这类应用都围绕一个简单的结构——**事件循环**（event loop）。事件循环的伪代码大致如下：

```c
while (1) {
    events = getEvents();
    for (e in events)
        processEvent(e);
}
```

真的就这么简单。主循环只是等待有活可干（即上面代码中的 `getEvents()`），然后对返回的每个事件逐一处理；处理每个事件的代码称为**事件处理器**（event handler）。关键在于：当一个处理器处理某个事件时，它是系统中唯一在运行的活动；因此，决定下一个处理哪个事件，就等价于调度。这种对调度的显式控制，正是基于事件的方法的根本优势之一。

但这段讨论留下了一个更大的问题：基于事件的服务器究竟如何判断发生了哪些事件，尤其是在网络和磁盘 I/O 方面？具体来说，事件服务器怎么知道有消息到达了？

## 33.2 一个重要的 API：select()（或 poll()）

有了基本的事件循环，接下来必须回答如何接收事件。在大多数系统上，都可以通过 `select()` 或 `poll()` 系统调用获得一套基本 API。

这些接口让程序做的事情很简单：检查是否有需要处理的传入 I/O。例如，设想一个网络应用（比如 Web 服务器）希望检查是否有网络分组到达，以便为它们提供服务。这些系统调用正好能干这件事。

以 `select()` 为例。手册页（在 Mac 上）是这样描述这个 API 的：

```c
int select(int nfds,
           fd_set *restrict readfds,
           fd_set *restrict writefds,
           fd_set *restrict errorfds,
           struct timeval *restrict timeout);
```

手册页上的原文描述是：`select()` 检查由 `readfds`、`writefds` 和 `errorfds` 传入地址的那些 I/O 描述符集合，看其中是否有描述符已可读、已可写，或有待处理的异常情况。

::: aside 阻塞接口与非阻塞接口

阻塞（同步）接口会把所有工作做完才返回给调用者；非阻塞（异步）接口则只是启动一些工作就立刻返回，让该做的工作在后台完成。阻塞调用的常见元凶是某种 I/O。例如，如果一次调用必须从磁盘读取才能完成，它就可能阻塞，等待已发给磁盘的 I/O 请求返回。非阻塞接口可以用在任何编程风格中（比如配合线程），但在基于事件的方法里是必不可少的，因为一次阻塞调用就会让所有进展停滞。

:::

每个集合中检查前 `nfds` 个描述符，也就是说，检查描述符集合中从 0 到 `nfds-1` 的描述符。返回时，`select()` 用“已就绪、可执行所请求操作的那些描述符”构成的子集替换传入的描述符集合。`select()` 返回所有集合中已就绪描述符的总数。

关于 `select()` 有几点要说。第一，注意它既能检查描述符是否可读，也能检查是否可写；前者让服务器判断有新分组到达、需要处理，后者则让服务知道何时可以回复（即出站队列没满）。

第二，注意 `timeout` 参数。一种常见用法是把超时设为 `NULL`，这会让 `select()` 无限期阻塞，直到某个描述符就绪。不过，更健壮的服务器通常会指定某种超时；一种常见做法是把超时设为零，从而让 `select()` 调用立即返回。

`poll()` 系统调用与之相当类似。细节请参阅它的手册页，或 Stevens 和 Rago 的书 [SR05]。

不管用哪个，这些基本原语都给了我们构建非阻塞事件循环的办法：简单地检查传入的分组，从有消息的套接字上读取数据，并按需回复。

::: tip 不要在基于事件的服务器中阻塞

基于事件的服务器能对任务调度进行细粒度控制。但要维持这种控制，就绝不能发起任何会阻塞调用者执行的调用；不遵守这条设计建议，结果就是一个被阻塞的基于事件的服务器、一群恼火的客户端，以及对你到底有没有读这本书这一部分的严重质疑。

:::

## 33.4 为什么更简单？不需要锁

在单 CPU 上运行基于事件的应用，并发程序里的那些问题就不再出现了。具体来说，由于一次只处理一个事件，就不需要获取或释放锁；基于事件的服务器不会被另一个线程打断，因为它毫无疑问是单线程的。因此，线程程序中常见的并发缺陷，在基本的基于事件的方法中不会显现出来。

## 33.5 一个问题：阻塞的系统调用

到目前为止，基于事件的编程听起来很棒，对吧？你写一个简单的循环，事件来了就处理。甚至根本不用考虑加锁！但有个问题：如果某个事件需要发起一个可能阻塞的系统调用，该怎么办？

例如，设想有个客户端请求到达服务器，要求从磁盘读取一个文件并把内容返回给客户端（很像一个简单的 HTTP 请求）。为处理这个请求，某个事件处理器最终得发起 `open()` 系统调用打开文件，接着是一系列 `read()` 调用读取文件。文件读入内存后，服务器多半会开始把结果发给客户端。

`open()` 和 `read()` 都可能向存储系统发出 I/O 请求（当所需的元数据或数据还不在内存中时），因此可能要花很长时间才能完成。对基于线程的服务器来说这不成问题：发起 I/O 请求的线程挂起（等待 I/O 完成）时，其他线程可以继续运行，服务器因此仍能推进。事实上，正是这种 I/O 与其他计算的自然重叠，让基于线程的编程显得自然又直白。

然而，在基于事件的方法里，没有别的线程可跑，只有主事件循环。这意味着，如果一个事件处理器发起了会阻塞的调用，整个服务器就会这样：一直阻塞到调用完成。事件循环一阻塞，系统就闲在那里，这是对资源的巨大潜在浪费。于是我们得到一条在基于事件系统中必须遵守的规则：不允许阻塞调用。

## 33.6 一种解决方案：异步 I/O

为了突破这个限制，许多现代操作系统引入了向磁盘系统发起 I/O 请求的新方式，统称为**异步 I/O**。这些接口让应用能在 I/O 完成之前就发出 I/O 请求，并立刻把控制权交还调用者；另一些接口则让应用能够判断各个 I/O 是否已完成。

例如，我们来看看 Mac 上提供的接口（其他系统有类似的 API）。这些 API 围绕一个基本结构展开，即 `struct aiocb`，通常称为 AIO 控制块。该结构的简化版本如下（更多信息请参阅手册页）：

```c
struct aiocb {
    int             aio_fildes;   // File descriptor
    off_t           aio_offset;   // File offset
    volatile void   *aio_buf;     // Location of buffer
    size_t          aio_nbytes;   // Length of transfer
};
```

要发起一次异步文件读取，应用应先把这个结构填好：要读取的文件的描述符（`aio_fildes`）、文件内的偏移量（`aio_offset`）、请求的长度（`aio_nbytes`），以及最后，读取结果应被复制到的目标内存位置（`aio_buf`）。

填好这个结构之后，应用必须发起异步读取调用；在 Mac 上，这个 API 就是异步读接口：

```c
int aio_read(struct aiocb *aiocbp);
```

这次调用尝试发出 I/O；如果成功，它立刻返回，应用（即基于事件的服务器）可以继续做自己的事。

不过，这个拼图还差最后一块：我们怎么知道某个 I/O 已经完成，从而 `aio_buf` 指向的缓冲区里现在已有请求的数据？

还需要最后一个 API。在 Mac 上，它（有点让人费解地）叫作 `aio_error()`。这个 API 长这样：

```c
int aio_error(const struct aiocb *aiocbp);
```

这个系统调用检查 `aiocbp` 所指的请求是否已完成。如果已完成，例程返回成功（用 0 表示）；如果未完成，返回 `EINPROGRESS`。因此，对于每一个尚未完成的异步 I/O，应用都可以通过调用 `aio_error()` 定期查询系统，判断该 I/O 是否已经完成。

你也许注意到了，检查 I/O 是否完成这件事很烦人：如果某个程序在某一时刻发出了几十上百个 I/O，它难道就一遍遍反复检查每一个，还是先等一会儿，还是……？

为解决这个问题，有些系统提供了基于中断的方法。该方法使用 UNIX 信号在异步 I/O 完成时通知应用，从而免去反复询问系统的必要。这种轮询与中断之争在设备中也能见到，你将在（或已经在）I/O 设备那一章看到。

在没有异步 I/O 的系统上，纯粹的基于事件的方法无法实现。不过，聪明的研究者已经推导出一些替代方案，效果相当不错。例如，Pai 等人 [PDZ99] 描述了一种混合方法：用事件处理网络分组，用线程池管理未完成的 I/O。细节请阅读他们的论文。

## 33.7 另一个问题：状态管理

基于事件方法的另一个问题是，这类代码通常比传统的基于线程的代码更难写。原因如下：当事件处理器发起异步 I/O 时，它必须打包一些程序状态，供 I/O 最终完成时下一个事件处理器使用；而在基于线程的程序里不需要这种额外工作，因为程序所需的状态就在线程的栈上。Adya 等人把这项工作称为**手工栈管理**（manual stack management），它是基于事件编程的根本所在 [A+02]。

为了把这个说法讲得更具体，我们看一个简单的例子：一个基于线程的服务器需要从文件描述符（`fd`）读取数据，读完后把读到的数据写入网络套接字描述符（`sd`）。代码（忽略错误检查）如下：

```c
int rc = read(fd, buffer, size);
rc = write(sd, buffer, size);
```

可以看到，在多线程程序中做这类工作轻而易举；当 `read()` 最终返回时，代码立刻知道该往哪个套接字写，因为这一信息就在线程的栈上（变量 `sd` 中）。

在基于事件的系统中，事情就没这么轻松了。要完成同样的任务，我们得先用上面描述的 AIO 调用异步发起读取。假定我们随后用 `aio_error()` 调用定期检查读取是否完成；当该调用告知读取已完成时，基于事件的服务器怎么知道接下来该做什么？

::: aside UNIX 信号

所有现代 UNIX 变体中都存在一套庞大而迷人的基础设施，称为**信号**（signal）。最简单的说法是，信号提供了一种与进程通信的方式。具体来说，信号可以被投递给应用；这样做会让应用停下手中的事情，转去运行**信号处理器**（signal handler），也就是应用里用来处理该信号的一段代码。处理完毕，进程就恢复先前的行为。每个信号都有名字，比如 `HUP`（挂断）、`INT`（中断）、`SEGV`（段违规）等；细节请参阅手册页。有趣的是，有时发出信号的正是内核自己。例如，当你的程序发生段违规时，操作系统会向它发送 `SIGSEGV`（在信号名前面加 `SIG` 是常见做法）；如果你的程序配置了捕获该信号，你实际上可以针对这种错误的程序行为运行一些代码（这对调试很有帮助）。当信号被发送给一个没有配置处理该信号的进程时，就会执行默认行为；对 `SEGV` 来说，进程会被杀死。下面是一个简单的程序，它进入无限循环，但事先设置好了捕获 `SIGHUP` 的信号处理器：

```c
void handle(int arg) {
    printf("stop wakin’ me up...\n");
}

int main(int argc, char *argv[]) {
    signal(SIGHUP, handle);
    while (1)
        ; // 除了收信号什么都不干
    return 0;
}
```

你可以用 `kill` 命令行工具向它发送信号（是的，这个名字既古怪又凶悍）。这样做会打断程序中的主 `while` 循环，运行处理器代码 `handle()`：

```c
prompt> ./main &
[3] 36705
prompt> kill -HUP 36705
stop wakin’ me up...
prompt> kill -HUP 36705
stop wakin’ me up...
```

关于信号还有很多要学，多到一章（更别说一页）远远不够。一如既往，有一个很好的来源：Stevens 和 Rago [SR05]。有兴趣就多读一些。

:::

如 Adya 等人所述 [A+02]，解决方案是使用一种古老的编程语言构造，称为**续延**（continuation）[FHK84]。听起来复杂，想法却很简单：基本上，把完成本事件处理所需的信息记录到某个数据结构中；当事件发生（即磁盘 I/O 完成）时，查出所需信息并处理该事件。

在这个具体例子中，解决办法是把套接字描述符（`sd`）记录到某种数据结构中（例如哈希表），以文件描述符（`fd`）为索引。当磁盘 I/O 完成时，事件处理器用文件描述符查出续延，续延会把套接字描述符的值返回给调用者。此时（终于），服务器就能完成最后一点工作，把数据写入套接字。

## 33.8 事件驱动方式仍然困难的地方

基于事件的方法还有几个难点值得提一下。例如，当系统从单 CPU 走向多 CPU 时，基于事件方法的一部分简单性就消失了。具体来说，为了利用多个 CPU，事件服务器必须并行运行多个事件处理器；这样做时，通常的同步问题（例如临界区）就会出现，必须采用通常的解决方案（例如锁）。因此，在现代多核系统上，不再可能用无锁的简单事件处理。

基于事件方法的另一个问题是，它与某些类型的系统活动（例如分页）配合得不好。例如，如果一个事件处理器发生缺页，它就会阻塞，服务器在缺页处理完成前无法推进。尽管服务器的结构已经刻意避免显式阻塞，这种由缺页造成的隐式阻塞却很难避免，一旦频繁出现，就会导致严重的性能问题。

第三个问题是，随着时间推移，基于事件的代码可能难以维护，因为各种例程的确切语义会发生变化 [A+02]。例如，如果某个例程从非阻塞变成阻塞，调用它的那个事件处理器也必须改变，以适应它的新性质——把自己拆成两半。由于阻塞对基于事件的服务器是灾难性的，程序员必须时刻留意每个事件所用 API 的语义是否发生了这类变化。

最后，尽管异步磁盘 I/O 如今在大多数平台上都已成为可能，但走到这一步花了很长时间 [PDZ99]，而且它从未像你可能设想的那样，以简单统一的方式与异步网络 I/O 结合。例如，人们本来只想用 `select()` 接口管理所有未完成的 I/O，但通常还是需要把网络用的 `select()` 和磁盘 I/O 用的 AIO 调用组合起来。

## 33.9 小结

我们初步介绍了一种基于事件的不同并发风格。基于事件的服务器把调度的控制权交给应用自身，但代价是复杂度上升，并且难以与现代系统的其他方面（例如分页）集成。由于这些挑战，还没有哪一种方法脱颖而出成为最优；因此在今后许多年里，线程和事件很可能作为同一个并发问题的两种不同解法继续并存。去读一些研究论文（例如 [A+02, PDZ99, vB+03, WCB01]），或者更好的是，亲手写一些基于事件的代码，来了解更多。

### 问题

1. 首先，写一个能接受并服务 TCP 连接的简单服务器。如果你还不会做这件事，得上网查一查。把它做成一次只服务一个请求；每个请求都很简单，例如获取当前时间。

2. 现在加入 `select()` 接口。构建一个能接受多个连接的主程序，以及一个事件循环：检查哪些文件描述符上有数据，然后读取并处理这些请求。务必仔细测试你使用 `select()` 的方式是否正确。

3. 接下来，让请求更有意思一点，模拟一个简单的 Web 服务器或文件服务器。每个请求都是读取某个文件（在请求中指定文件名）的内容，服务器应把文件读入缓冲区，然后把内容返回给客户端。用标准的 `open()`、`read()`、`close()` 系统调用来实现这个功能。这里要小心一点：如果你让它长期运行，可能有人会想办法利用它读取你电脑上的所有文件！

4. 现在，不要用标准的 I/O 系统调用，改用本章描述的异步 I/O 接口。把异步接口引入你的程序有多难？

5. 为了好玩，给代码加一些信号处理。信号的一种常见用途是通知服务器重新加载某种配置文件，或执行其他管理动作。也许一个自然的玩法是给服务器加一个用户级文件缓存，存放最近访问过的文件。实现一个信号处理器，在收到信号时清空缓存。

6. 最后是困难的部分：你怎么判断构建异步、基于事件的方法所付出的努力是否值得？你能设计一个实验来展示它的好处吗？你的方法增加了多少实现复杂度？

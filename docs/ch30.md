# 第 30 章　条件变量

<div class="chap-en">Condition Variables</div>

到目前为止，我们已经建立了锁的概念，也看到只要把硬件支持和操作系统支持恰当地组合起来，就能把锁正确构造出来。遗憾的是，锁并不是编写并发程序所需的唯一原语。

具体来说，有很多场合线程希望在继续执行之前先检查某个条件是否成立。例如，父线程可能想先确认子线程已经完成，然后才继续（这一般称为 `join()`）；这样的等待该怎么实现呢？我们来看图 30.1。

我们真正想要的是一种办法，让父线程先睡下，等到它所等待的条件（比如子线程执行完毕）成立时再被唤醒。

::: crux 如何等待一个条件

在多线程程序里，线程先等待某个条件成立、再继续往下走，往往很有用。最朴素的做法是一直自旋到条件成立，这极其低效、浪费 CPU 周期，某些情况下还是错的。那么，线程究竟该如何等待一个条件呢？
:::

## 30.1 定义与例程

要等待某个条件成立，线程可以利用所谓的**条件变量**（condition variable）。条件变量是一个显式的队列：当某个执行状态（也就是某个条件）不合意时，线程可以把自身挂到这个队列上（在该条件上**等待**）；而当另一个线程改变了这个状态之后，就可以唤醒其中一个（或多个）等待的线程，让它们继续运行（在该条件上**发信号**）。这个想法可以追溯到 Dijkstra 对“私有信号量”的使用 [D68]；类似的想法后来被 Hoare 在他关于管程的工作中命名为“条件变量” [H74]。

声明这样一个条件变量，只要写 `pthread_cond_t c;` 就够了，它把 `c` 声明为一个条件变量（注意：还需要正确地初始化）。条件变量上关联着两个操作：`wait()` 和 `signal()`。`wait()` 在线程想让自己睡眠时调用；`signal()` 则在线程改变了程序中的某些东西、想唤醒一个睡在该条件上的线程时调用。

```c
int done
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t c
= PTHREAD_COND_INITIALIZER;
void thr_exit() {
Pthread_mutex_lock(&m);
done = 1;
Pthread_cond_signal(&c);
Pthread_mutex_unlock(&m);
void *child(void *arg) {
printf("child\n");
thr_exit();
return NULL;
void thr_join() {
Pthread_mutex_lock(&m);
while (done == 0)
Pthread_cond_wait(&c, &m);
Pthread_mutex_unlock(&m);
int main(int argc, char *argv[]) {
printf("parent: begin\n");
pthread_t p;
Pthread_create(&p, NULL, child, NULL);
thr_join();
printf("parent: end\n");
return 0;
```

<div class="code-cap"><span class="code-label">图 30.3</span>父线程等待子线程：使用条件变量</div>

具体来说，POSIX 中的调用长这样：

```c
pthread_cond_wait(pthread_cond_t *c, pthread_mutex_t *m);
pthread_cond_signal(pthread_cond_t *c);
```

为简便起见，我们通常把它们称作 `wait()` 和 `signal()`。关于 `wait()` 你可能会注意到一点：它还要接收一个互斥锁作为参数，并且假定调用 `wait()` 时这把锁已经被持有。`wait()` 的职责是（原子地）释放这把锁并让调用线程睡眠；当线程被唤醒后（某个其他线程向它发了信号），它必须在返回调用者之前重新获取这把锁。之所以有这种复杂性，是为了防止线程在试图让自己睡眠时出现某些竞态条件。我们来看看 join 问题的解法（图 30.3），以便更好地理解这一点。

有两种情况需要考虑。第一种，父线程创建了子线程之后自己继续运行（假定我们只有一个处理器），于是立即调用 `thr_join()` 等待子线程结束。此时它会获取锁，检查子线程是否完成（还没有），然后调用 `wait()` 让自己睡眠（同时释放锁）。子线程最终会运行，打印 “child”，并调用 `thr_exit()` 唤醒父线程；这段代码只是获取锁、把状态变量 `done` 置位，然后向父线程发信号把它唤醒。最后，父线程继续运行（从 `wait()` 返回时已重新持有锁），释放锁，打印最后一条消息 “parent: end”。

第二种，子线程在创建后立刻运行，把 `done` 置为 1，调用 signal 想唤醒一个睡眠中的线程（但并没有这样的线程，于是直接返回），然后就结束了。父线程随后运行，调用 `thr_join()`，看到 `done` 为 1，于是不等待，直接返回。

最后还有一点：你可能会发现，父线程在决定是否等待条件时用的是 while 循环，而不是简单的 if 语句。按这个程序的逻辑看，这似乎并非严格必要，但这始终是个好习惯，下文我们会看到原因。

为了确保你理解 `thr_exit()` 和 `thr_join()` 中每一段代码的重要性，我们来试几种替代写法。首先，你可能会问：真的需要状态变量 `done` 吗？如果代码写成下面这样呢？（图 30.4）

很遗憾，这种写法是错的。设想子线程立刻运行、立即调用 `thr_exit()` 的情形：此时子线程会发信号，但条件上并没有睡着的线程。等父线程运行起来，它只会调用 wait，然后卡在那里，再没有线程会唤醒它。从这个例子你应该体会到状态变量 `done` 的重要性：它记录了线程所关心的那个值。睡眠、唤醒和加锁，全都是围绕它构建起来的。

```c
void thr_exit() {
Pthread_mutex_lock(&m);
Pthread_cond_signal(&c);
Pthread_mutex_unlock(&m);
void thr_join() {
Pthread_mutex_lock(&m);
Pthread_cond_wait(&c, &m);
Pthread_mutex_unlock(&m);
```

这里（图 30.5）是另一种糟糕的实现。这个例子里，我们设想发信号和等待都不需要持锁。会出什么问题呢？想一想吧¹！

问题在于一个微妙的竞态条件。具体来说，如果父线程调用 `thr_join()`，然后检查 `done` 的值，它会看到值为 0，于是准备去睡眠。但就在它调用 wait 进入睡眠之前，父线程被中断，子线程运行了。子线程把状态变量 `done` 改成 1 并发出信号，但没有线程在等待，所以没有线程被唤醒。等父线程再次运行时，它就会永远睡下去，这是个严重的错误。

希望你从这个简单的 join 例子中已经看出正确使用条件变量的一些基本要求。为了确保你理解，下面我们来看一个更复杂的例子：生产者 / 消费者问题，也叫有界缓冲区问题。

::: tip 发信号时始终持有锁

尽管并非所有情况下都严格必要，但在使用条件变量时，发信号时持有锁多半是最简单也最好的做法。上面的例子展示了一种必须持锁才能保证正确性的情形；另一些情形下不持锁大概也没问题，但那仍然是你应当避免的。所以为简单起见，调用 signal 时请持锁。这条提示的反面，也就是调用 wait 时持有锁，就不只是提示了，而是由 `wait` 的语义强制要求的，因为 `wait` 总是（a）假定调用时锁已被持有，（b）在让调用者睡眠时释放该锁，（c）在返回之前重新获取该锁。因此，把这条提示推广一下是成立的：调用 signal 或 wait 时都持有锁，你就总不会出问题。
:::

## 30.2 生产者 / 消费者（有界缓冲区）问题

本章要面对的第二个同步问题叫作生产者 / 消费者问题，有时也叫有界缓冲区问题，最早由 Dijkstra 提出 [D72]。事实上，正是这个生产者 / 消费者问题促使 Dijkstra 和他的同事们发明了广义信号量（它既可以当锁用，也可以当条件变量用）[D01]；关于信号量，我们后面会了解更多。

设想有一个或多个生产者线程，以及一个或多个消费者线程。生产者生成数据项并放入缓冲区；消费者从缓冲区取出这些数据项，以某种方式消费掉。

这种安排在真实系统中随处可见。例如在一个多线程 Web 服务器里，生产者把 HTTP 请求放进工作队列（也就是有界缓冲区）；消费者线程从这个队列里取出请求并处理。

当你把一个程序的输出通过管道接到另一个程序时，用到的也是有界缓冲区，比如 `grep foo file.txt | wc -l`。这个例子并发地运行两个进程：`grep` 把 `file.txt` 中含有字符串 `foo` 的行写到它认为的标准输出；UNIX shell 把这股输出重定向到一个所谓的 UNIX 管道（由 `pipe` 系统调用创建）。管道的另一端连着 `wc` 进程的标准输入，而 `wc` 只是统计输入流的行数并打印结果。于是，`grep` 进程是生产者，`wc` 进程是消费者，两者之间是一个位于内核中的有界缓冲区；而在这个例子里，你只是个坐享其成的用户。

因为有界缓冲区是共享资源，我们当然必须要求对它的访问是同步的，否则² 就会出现竞态条件。为了更好地理解这个问题，我们来看一些实际的代码。

我们首先需要一个共享缓冲区，生产者往里放数据，消费者从中取数据。为简单起见，就用一个整数（你完全可以想象，这个位置放的是指向某个数据结构的指针），再加上两个内部例程，分别往共享缓冲区里放值、从中取值。细节见图 30.6（第 6 页）。

很简单吧？`put()` 例程假定缓冲区是空的（并用断言检查这一点），然后简单地把值放进共享缓冲区，并把 `count` 置为 1，标记其为满。`get()` 例程则相反，把缓冲区置为空（也就是把 `count` 设为 0）并返回取到的值。别担心这个共享缓冲区只有一个槽位；后面我们会把它推广成能容纳多个条目的队列，那会比听起来更有意思。

现在需要写一些例程，用来判断什么时候可以访问缓冲区，是往里放数据还是从中取数据。条件应该很显然：只有当 `count` 为零（也就是缓冲区为空）时才能往缓冲区放数据，只有当 `count` 为 1（也就是缓冲区为满）时才能从缓冲区取数据。如果我们写出的同步代码让生产者往满的缓冲区里放数据，或者让消费者从空的缓冲区取数据，那就做错了（在这份代码里，断言会触发）。

这项工作由两类线程完成，一类我们称为生产者线程，另一类称为消费者线程。图 30.7 给出了生产者的代码——它把整数放进共享缓冲区，循环 `number` 次；以及消费者的代码——它从共享缓冲区取出数据（永远循环），每次都打印出从缓冲区取到的数据项。

**一个有问题的解法**　现在设想我们只有一个生产者和一个消费者。显然 `put()` 和 `get()` 例程里都有临界区，因为 `put()` 更新缓冲区，而 `get()` 从中读取。但是，光在代码外面套一把锁并不管用；我们还需要别的东西。

不出所料，这个“别的东西”就是条件变量。在这个（有问题的）第一次尝试中（图 30.8），我们用一个条件变量 `cond` 以及与之关联的锁 `mutex`。

我们来分析生产者和消费者之间的信号逻辑。生产者想填满缓冲区时，等待缓冲区为空（p1–p3）。消费者的逻辑完全一样，但等待的是另一个条件：缓冲区为满（c1–c3）。

如果只有一个生产者和一个消费者，图 30.8 的代码是能工作的。但如果我们有不止一个这类线程（比如两个消费者），这个解法就有两个致命问题。是哪两个呢？

……（在这里停下来想一想）…… 先看第一个问题，它与 wait 之前的 if 语句有关。假设有两个消费者（Tc1 和 Tc2）和一个生产者（Tp）。首先，一个消费者（Tc1）运行；它获取锁（c1），检查是否有缓冲区可供消费（c2），发现没有，于是等待（c3）（这会释放锁）。

接着生产者（Tp）运行。它获取锁（p1），检查是否所有缓冲区都满了（p2），发现不是，于是继续把缓冲区填满（p4）。然后生产者发出“某个缓冲区已被填满”的信号（p5）。关键在于，这把第一个消费者（Tc1）从在条件变量上睡眠移到了就绪队列；Tc1 现在可以运行了（但还没真正运行）。生产者接着往下走，直到发现缓冲区已满，于是睡眠（p6、p1–p3）。

问题就出在这里：另一个消费者（Tc2）溜了进来，把这一个值消费掉了（c1、c2、c4、c5、c6，因为缓冲区是满的，跳过了 c3 处的 wait）。现在假设 Tc1 运行；就在从 wait 返回之前，它重新获取锁，然后返回。接着它调用 `get()`（c4），可已经没有缓冲区可供消费了！断言被触发，代码没能按预期工作。显然，我们本该想办法阻止 Tc1 去消费，因为 Tc2 溜进来吃掉了缓冲区里那个刚被生产出来的值。图 30.9 展示了每个线程的动作，以及它们随时间变化的调度器状态（就绪、运行或睡眠）。

问题的成因很简单：在生产者唤醒 Tc1 之后、Tc1 真正运行之前，有界缓冲区的状态（拜 Tc2 所赐）已经变了。发信号给一个线程只是把它唤醒；它仅仅是一个“世界状态已经变了”的提示（在这个例子里，是有值被放进了缓冲区），但并无法保证被唤醒的线程运行时状态仍如其所愿。这种对 signal 含义的解释，通常称为 **Mesa 语义**，得名于最早以这种方式构建条件变量的那项研究 [LR80]；与之相对的叫 **Hoare 语义**，实现起来更难，但能提供更强的保证——被唤醒的线程会在被唤醒后立即运行 [H74]。几乎所有已建成的系统采用的都是 Mesa 语义。

**好一些，但仍有问题：用 while，而不是 if**　幸运的是，这个修补很简单（图 30.10）：把 if 改成 while。想想它为什么有效：现在消费者 Tc1 醒来后，（在持有锁的情况下）会立即重新检查共享变量的状态（c2）。如果此时缓冲区是空的，消费者就重新睡回去（c3）。生产者里对应的 if 也改成了 while（p2）。

拜 Mesa 语义所赐，使用条件变量时有一条要记住的简单规则：总是用 while 循环。有时你其实不必重新检查条件，但这样做总是安全的；照做就好，皆大欢喜。

我们这就来确认一下你想对了没有，或者干脆确认一下你现在还醒着、还在读这部分内容。问题出现在两个消费者（Tc1 和 Tc2）先运行、并且都去睡眠（c3）的时候。然后生产者运行，往缓冲区里放了一个值，并唤醒其中一个消费者（比如 Tc1）。生产者接着循环回去（途中释放并重新获取锁），想再往缓冲区里放数据；由于缓冲区已满，生产者改为在条件上等待（于是睡眠）。现在，一个消费者（Tc1）就绪，两个线程（Tc2 和 Tp）睡在条件上。我们马上就要制造麻烦了：场面开始刺激起来！

消费者 Tc1 随后从 `wait()` 返回而醒来（c3），重新检查条件（c2），发现缓冲区是满的，于是取走那个值（c4）。关键就在这里：这个消费者接着在条件上发信号（c5），只唤醒一个睡眠中的线程。可是，它该唤醒哪一个呢？

因为消费者已经把缓冲区清空了，它显然应该唤醒生产者。然而，如果它唤醒的是消费者 Tc2（这完全可能，取决于等待队列是怎么管理的），我们就麻烦了。具体来说，消费者 Tc2 会醒来，发现缓冲区是空的（c2），于是又睡回去（c3）。而生产者 Tp，手上还有一个值要放进缓冲区，却仍然睡着。

另一个消费者线程 Tc1 也睡回去了。三个线程全都睡死过去，这显然是 bug；这场灾难的逐步细节，见图 30.11 中残酷的演示。

发信号显然是必要的，但必须更有针对性。消费者不该唤醒其他消费者，只该唤醒生产者，反之亦然。

**单缓冲区的生产者 / 消费者解法**　这里的解法同样很小：用两个条件变量代替一个，从而在系统状态变化时正确地指明该唤醒哪一类线程。图 30.12 给出了相应的代码。

在这份代码里，生产者线程在条件 `empty` 上等待，并发出 `fill` 信号。反过来，消费者线程在 `fill` 上等待，并发出 `empty` 信号。这样一来，上面的第二个问题就在设计上被避免了：消费者绝不会误唤醒消费者，生产者绝不会误唤醒生产者。

::: tip 检查条件时用 while（而不是 if）

在多线程程序里检查条件时，用 while 循环总是正确的；而用 if 语句只有在特定语义下才可能正确。所以，总是用 while，你的代码就会按预期工作。在条件检查外面套 while 循环，还能应对虚假唤醒的情况。在某些线程库中，由于实现细节，可能只发了一次信号却有两个线程被唤醒 [L11]。虚假唤醒正是要重新检查线程所等条件的又一个理由。

**正确的生产者 / 消费者解法**　现在我们有了一个能正常工作的生产者 / 消费者解法，虽然还不够通用。最后一处改动是为了获得更高的并发度和效率：具体说，我们增加更多缓冲区槽位，这样就可以连续生产多个值再睡眠，同样也可以连续消费多个值再睡眠。只有一个生产者和一个消费者时，这种做法效率更高，因为它减少了上下文切换；有多个生产者或消费者（或者两者都有）时，它还允许生产或消费并发进行，从而进一步提高并发度。幸运的是，相对当前解法这只是很小的改动。

## 30.3 覆盖条件

下面再看一个条件变量用法的例子。这段代码研究取自 Lampson 和 Redell 关于 Pilot 的论文 [LR80]——正是最早实现上文所述 Mesa 语义的那批人（他们用的语言叫 Mesa，名字便由此而来）。

他们遇到的问题最好用一个简单的例子来说明，这里是一个简单的多线程内存分配库。图 30.15 展示了一段（简化过的）代码片段，用来说明这个问题。

你大概能看出来，当线程调用内存分配代码时，它可能需要等待，直到有更多内存被释放出来。反过来，当线程释放内存时，它会发信号表示有更多空闲内存了。然而，上面的代码有个问题：该唤醒哪个等待的线程（可能不止一个）呢？

考虑下面这个场景。假设当前空闲字节数为零；线程 Ta 调用 `allocate(100)`，接着线程 Tb 调用 `allocate(10)`，申请更少的内存。于是 Ta 和 Tb 都在条件上等待并睡去；没有足够的空闲字节能满足其中任何一个请求。

这时，假设第三个线程 Tc 调用 `free(50)`。不幸的是，当它调用 signal 想唤醒一个等待的线程时，未必会唤醒正确的那个线程 Tb——Tb 只等 10 个字节被释放；而 Ta 应当继续等待，因为空闲内存还不够。所以图中的代码不管用，因为发起唤醒的线程并不知道该唤醒哪个（或哪些）线程。

Lampson 和 Redell 建议的解法很直截了当：把上面代码里的 `pthread_cond_signal()` 调用换成 `pthread_cond_broadcast()`，它会唤醒所有等待的线程。这样一来，我们保证了所有该被唤醒的线程都会被唤醒。当然，代价是性能可能受影响，因为我们可能白白唤醒许多（暂时）不该醒来的线程。这些线程只会醒来、重新检查条件，然后立刻又睡回去。

Lampson 和 Redell 把这样的条件称为**覆盖条件**（covering condition），因为它（保守地）覆盖了所有线程需要被唤醒的情形；代价如前所述，就是可能唤醒过多的线程。眼光敏锐的读者可能还注意到，我们本可以在更早的地方就用这个办法（想想只有一个条件变量的生产者 / 消费者问题）。不过在那种情况下，我们有更好的解法可用，所以用了它。一般来说，如果你发现程序只有把 signal 改成 broadcast 才能正常工作（而你认为本不该如此），那你八成有个 bug；去修好它！但在像上面内存分配器这样的情形里，broadcast 可能就是最直截了当的解法。

## 30.4 小结

本章介绍了锁之外的另一个重要的同步原语：条件变量。通过允许线程在某个程序状态不合意时睡眠，条件变量（CV）使我们能够干净利落地解决若干重要的同步问题，包括那个著名（且依然重要）的生产者 / 消费者问题，以及覆盖条件。这里本该放一句更有戏剧性的收尾，比如“他热爱老大哥” [O49]。

# 第 31 章　信号量

<div class="chap-en">Semaphores</div>

<div class="chap-en">Semaphores</div>

如今我们已经知道，要解决广泛而有趣的并发问题，锁和条件变量两者缺一不可。多年前最早意识到这一点的人之一就是 Edsger Dijkstra（不过确切的历史很难考证 [GR92]）。他为人所知的事情很多，比如图论中著名的“最短路径”算法 [D59]、早期那篇关于结构化编程的檄文《Goto 语句被认为有害》[D68a]（多好的标题！），以及我们这里要研究的：他提出了一种称为**信号量**（semaphore）的同步原语 [D68b, D72]。事实上，Dijkstra 和他的同事发明信号量，本意是用单独一个原语来应付所有与同步有关的事情；你将会看到，信号量既能当锁用，也能当条件变量用。

## 31.1 信号量：定义

信号量是一个带有整数值的对象，我们可以用两个例程来操作它；在 POSIX 标准中，这两个例程是 `sem_wait()` 和 `sem_post()`¹。由于信号量的初始值决定了它的行为，所以在调用任何其他例程与信号量打交道之前，我们必须先把它初始化为某个值，就像图 31.1 的代码所做的那样。

```c
#include <semaphore.h>
sem_t s;
sem_init(&s, 0, 1);
```

<div class="code-cap"><span class="code-label">图 31.1</span>初始化一个信号量</div>

这段代码声明了一个信号量 `s`，并把 1 作为第三个参数传进去，从而把它初始化为 1。在我们将看到的所有例子里，`sem_init()` 的第二个参数都设为 0，表示这个信号量在同一进程的多个线程之间共享。这个参数的其他用法（也就是如何用信号量在不同进程之间同步访问）详见 man 手册，那些用法需要给第二个参数传一个不同的值。

信号量初始化之后，我们就可以调用两个函数之一与它交互：`sem_wait()` 或 `sem_post()`。这两个函数的行为见图 31.2。

眼下我们先不关心这些例程的实现，它们的实现显然需要小心处理：当多个线程同时调用 `sem_wait()` 和 `sem_post()` 时，显然需要管好这些临界区。现在我们先集中精力看如何使用这些原语；稍后再讨论它们是怎么造出来的。

这里先说明这套接口的几个要点。第一，`sem_wait()` 要么立即返回（因为我们调用 `sem_wait()` 时信号量的值大于等于 1），要么让调用者挂起执行，等待随后的某次 post。当然，可能有多个线程同时调用 `sem_wait()`，于是它们都排队等着被唤醒。

第二，`sem_post()` 不像 `sem_wait()` 那样要等某个特定条件成立才继续。它只是把信号量的值加一，然后如果有线程在等着被唤醒，就唤醒其中一个。

第三，信号量的值为负数时，其绝对值正好等于正在等待的线程数 [D68b]。虽然信号量的使用者通常看不到这个值，但这条不变式值得了解，或许还能帮你记住信号量是怎么工作的。

```c
int sem_wait(sem_t *s) {
decrement the value of semaphore s by one
wait if value of semaphore s is negative
int sem_post(sem_t *s) {
increment the value of semaphore s by one
if there are one or more threads waiting, wake one
```

更有意思的情形是：Thread 0 “持有锁”（也就是它已经调用 `sem_wait()` 但还没调用 `sem_post()`），而另一个线程（Thread 1）调用 `sem_wait()` 想进入临界区。这时 Thread 1 会把信号量的值减到 -1，于是等待（自己睡眠，让出处理器）。等 Thread 0 再次运行，它最终会调用 `sem_post()`，把信号量的值加回 0，然后唤醒等待的线程（Thread 1），Thread 1 于是能够拿到锁。Thread 1 完成后同样会把信号量的值加一，重新变回 1。

这样我们就能把信号量当锁用了。由于锁只有两种状态（被持有和未被持有），我们有时把用作锁的信号量称为**二值信号量**（binary semaphore）。注意，如果你只以这种二值方式使用信号量，那么它的实现可以比我们这里讨论的通用信号量简单得多。

## 31.3 用信号量实现顺序

信号量还可以用来给并发程序中的事件排序。比如，某个线程可能想等一个链表变成非空，然后从中删除元素。在这种用法中，通常是一个线程在等待某件事发生，另一个线程让这件事发生，然后发出信号表示它已经发生，从而唤醒等待的线程。这样，我们就是把信号量当作一种排序原语来用（类似于前面用条件变量的做法）。

一个简单的例子如下。设想一个线程创建了另一个线程，然后想等它执行完毕（图 31.6）。程序运行时，我们希望看到：

```c
sem_t s;
void *child(void *arg) {
printf("child\n");
sem_post(&s); // signal here: child is done
return NULL;
int main(int argc, char *argv[]) {
sem_init(&s, 0, X); // what should X be?
printf("parent: begin\n");
pthread_t c;
Pthread_create(&c, NULL, child, NULL);
sem_wait(&s); // wait here for child
printf("parent: end\n");
return 0;
```

<div class="code-cap"><span class="code-label">图 31.6</span>父线程等待子线程</div>

```c
parent: begin
parent: end
```

那么问题就是：怎样用信号量达到这个效果？答案其实比较容易理解。如代码所示，父线程只是调用 `sem_wait()`，子线程调用 `sem_post()`，以此等待“子线程执行完毕”这个条件成立。但这又带来一个问题：这个信号量的初始值该是多少？

（还是先想一想，别急着往下读）答案当然是 0。有两种情况要考虑。第一种，假设父线程创建了子线程，但子线程还没运行（也就是它待在就绪队列里没有运行）。这时（图 31.7），父线程会在子线程调用 `sem_post()` 之前就调用 `sem_wait()`；我们希望父线程等子线程运行。要让这件事发生，唯一的办法是信号量的值不大于 0；所以初始值是 0。父线程运行，把信号量减到 -1，然后等待（睡眠）。等子线程终于运行，它会调用 `sem_post()`，把信号量的值加到 0，并唤醒父线程，父线程于是从 `sem_wait()` 返回，结束程序。

第二种情况（图 31.8）是子线程先运行完，父线程还没来得及调用 `sem_wait()`。这时子线程先调用 `sem_post()`，把信号量的值从 0 加到 1。等父线程得到机会运行，它调用 `sem_wait()`，发现信号量的值是 1；于是父线程把值减到 0 并立即返回，不必等待，同样达到了预期的效果。

## 31.4 生产者/消费者（有界缓冲区）问题

本章要面对的下一个问题，是**生产者/消费者**问题，有时也叫**有界缓冲区**问题 [D72]。上一章讲条件变量时已经详细描述过这个问题，细节请参看那里。

::: tip 设置信号量的值

我们已经看到两个初始化信号量的例子。第一个把值设为 1，把信号量当锁用；第二个设为 0，用来给事件排序。那么初始化信号量的一般规则是什么？有一个简单的思路，要感谢 Perry Kivolowitz：想一想初始化之后你愿意立刻送出多少个资源。用锁的时候是 1，因为你愿意让锁在初始化之后马上就被锁上（送出去）。排序那个例子里是 0，因为一开始没有任何东西可以送出；只有子线程完成时资源才被创造出来，那时值才加到 1。以后再遇到信号量问题，试试这条思路，看看是否管用。

:::

在这个例子里，生产者先等某个缓冲区变空，以便把数据放进去；消费者同样先等某个缓冲区被填满，然后才使用它。我们先设想 MAX=1（数组中只有一个缓冲区），看看这样是否可行。

再一次设想有两个线程：一个生产者、一个消费者。我们在单个 CPU 上考察一个具体场景。假设消费者先运行。于是消费者会执行图 31.10 的 C1 行，调用 `sem_wait(&full)`。由于 `full` 被初始化为 0，这次调用会把 `full` 减到 -1，让消费者阻塞，等待另一个线程对 `full` 调用 `sem_post()`，这正是我们想要的效果。

接着假设生产者运行。它会执行 P1 行，调用 `sem_wait(&empty)`。与消费者不同，生产者在这一行会继续往下走，因为 `empty` 被初始化为 MAX（本例中是 1）。于是 `empty` 被减到 0，生产者把一个数据值放进缓冲区的第一个条目（P2 行）。然后生产者继续执行 P3 行，调用 `sem_post(&full)`，把 `full` 信号量的值从 -1 改成 0，并唤醒消费者（例如把它从阻塞状态移到就绪状态）。

这时可能发生两种情况之一。如果生产者继续运行，它会循环回到 P1 行，但这一次会阻塞，因为 `empty` 信号量的值是 0。如果生产者被中断而消费者开始运行，消费者会从 `sem_wait(&full)`（C1 行）返回，发现缓冲区里有数据，于是消费掉它。两种情况都达到了我们想要的效果。

你可以用更多线程（比如多个生产者、多个消费者）推演同一个例子。它应该仍然能工作。

### 避免死锁

好，既然你想明白了，下面是答案。设想两个线程，一个生产者、一个消费者。消费者先运行。它获取互斥锁（C0 行），然后在 `full` 信号量上调用 `sem_wait()`（C1 行）；由于此时还没有数据，这次调用让消费者阻塞，从而让出 CPU；关键在于，消费者此时仍然持有锁。

接着生产者运行。它有数据要生产，如果它能运行，就能唤醒消费者线程，一切都会很顺利。不幸的是，它做的第一件事就是在二值互斥信号量上调用 `sem_wait()`（P0 行）。锁已经被持有了，于是生产者现在也卡住等待。

这里形成了一个简单的循环。消费者持有互斥锁，等着有人给 `full` 发信号；生产者可以给 `full` 发信号，却在等互斥锁。于是生产者和消费者互相等待：典型的死锁。

### 最后，一个可行的方案

要解决这个问题，我们只需缩小锁的作用范围。图 31.12 给出了正确的方案。如你所见，我们只是把互斥锁的获取和释放挪到临界区周围；对 `full` 和 `empty` 的等待与发信号代码留在锁外面²。结果就是一个简单而可用的有界缓冲区，这是多线程程序里常用的模式。现在就把它弄懂，以后拿去用。往后很多年你都会为此感谢我们。或者至少，在期末考试或求职面试问到同样问题时，你会感谢我们。

## 31.5 读写锁

另一个经典问题来自一种愿望：希望有一种更灵活的锁原语，承认对数据结构的不同访问可能需要不同种类的加锁方式。举个例子，设想若干并发的链表操作，包括插入和简单的查找。插入会改变链表的状态（所以用传统的临界区是合理的），而查找只是读取数据结构；只要我们能保证没有插入正在进行，就可以让许多查找并发进行。我们接下来要开发的、支持这类操作的特殊锁，叫做**读写锁**（reader-writer lock）[CHP71]。这种锁的代码见图 31.13。

代码相当简单。如果某个线程想更新这个数据结构，就该调用新的一对同步操作：`rwlock_acquire_writelock()` 获取写锁，`rwlock_release_writelock()` 释放写锁。内部实现上，它们只是用 `writelock` 信号量保证只有一个写者能拿到锁，从而进入临界区更新数据结构。

更有意思的是获取和释放读锁的那对例程。获取读锁时，读者先获取 `lock`，然后递增 `readers` 变量，记录当前有多少读者在这个数据结构里。`rwlock_acquire_readlock()` 里关键的一步发生在第一个读者获取锁的时候；这种情况下，该读者还要通过对 `writelock` 信号量调用 `sem_wait()` 来获取写锁，然后再调用 `sem_post()` 释放 `lock`。

于是，一旦某个读者拿到了读锁，更多读者也能拿到读锁；而任何想获取写锁的线程都必须等所有读者都结束，最后一个离开临界区的读者对 `writelock` 调用 `sem_post()`，从而让某个等待的写者能够拿到锁。

这种做法（如我们所愿）能工作，但确实有些缺点，尤其是在公平性方面。特别是读者很容易让写者**饥饿**。这个问题有更精细的解法；也许你能想出一个更好的实现？提示：想一想，一旦有写者在等待，你需要做什么才能阻止更多读者进入。

```c
typedef struct _rwlock_t {
sem_t lock;
// binary semaphore (basic lock)
sem_t writelock; // allow ONE writer/MANY readers

// #readers in critical section
} rwlock_t;
void rwlock_init(rwlock_t *rw) {
rw->readers = 0;
sem_init(&rw->lock, 0, 1);
sem_init(&rw->writelock, 0, 1);
void rwlock_acquire_readlock(rwlock_t *rw) {
sem_wait(&rw->lock);
rw->readers++;
if (rw->readers == 1) // first reader gets writelock
sem_wait(&rw->writelock);
sem_post(&rw->lock);
void rwlock_release_readlock(rwlock_t *rw) {
sem_wait(&rw->lock);
rw->readers--;
if (rw->readers == 0) // last reader lets it go
sem_post(&rw->writelock);
sem_post(&rw->lock);
void rwlock_acquire_writelock(rwlock_t *rw) {
sem_wait(&rw->writelock);
void rwlock_release_writelock(rwlock_t *rw) {
sem_post(&rw->writelock);
```

最后要指出，使用读写锁应当谨慎。它们往往带来更多开销（尤其是更精细的实现），因此相比只用简单快速的加锁原语，并不一定能提升性能 [CB08]。无论如何，它们又一次展示了我们能用信号量做出多么有趣而实用的东西。

::: tip 简单而笨拙往往更好（希尔定律）

千万不要低估“简单笨拙的办法可能是最好的办法”这个想法。就加锁而言，有时简单的自旋锁效果最好，因为它容易实现、速度又快。读写锁之类的东西听起来很酷，但它们复杂，而复杂可能就意味着慢。所以，永远先试试简单笨拙的办法。这种推崇简单的思想在很多地方都能见到。一个早期来源是 Mark Hill 的博士论文 [H87]，研究的是如何为 CPU 设计缓存。Hill 发现，简单的直接映射缓存比花哨的组相联设计效果更好（原因之一是：在缓存中，更简单的设计能让查找更快）。Hill 把自己的工作简洁地总结为：“又大又笨更好。”于是我们把类似的建议称为**希尔定律**（Hill's Law）。

:::

## 31.6 哲学家就餐

由 Dijkstra 提出并解决过的最著名的并发问题之一，叫做**哲学家就餐**问题 [D71]。这个问题出名是因为它好玩，也在智力上有点意思；不过它的实用价值很低。但它实在太有名，所以非得放进来；确实，你可能会在面试中被问到它，要是因为答不上来而错过那份工作，你会恨死你的操作系统老师的。反过来，如果你拿到了工作，请务必给你的操作系统老师寄一张感谢便条，或者送点股票期权。

问题的基本设定是这样（如图 31.14 所示）：假设有五位“哲学家”围坐在桌旁。每两位哲学家之间放一把叉子（因此总共五把）。每位哲学家都有思考的时间（此时不需要叉子）和吃饭的时间。要吃饭，哲学家需要两把叉子，左边一把、右边一把。对这些叉子的争用，以及由此产生的同步问题，正是我们要在并发编程中研究它的原因。

下面是每位哲学家的基本循环，假设每位都有一个 0 到 4（含）的唯一线程标识 p：

```c
while (1) {
think();
get_forks(p);
eat();
put_forks(p);
```

<div class="code-cap"><span class="code-label">图 31.14</span>哲学家就餐</div>

那么，关键的挑战就是写出 `get_forks()` 和 `put_forks()`，使得不会死锁、没有哲学家饿死吃不上饭，并且并发度高（也就是尽可能多的哲学家能同时吃饭）。

沿用 Downey 的解法 [D08]，我们用几个辅助函数把思路铺开。它们是：

```c
int left(int p)
{ return p; }
int right(int p) { return (p + 1) % 5; }
```

当哲学家 p 想引用左边的叉子时，调用 `left(p)` 即可。类似地，哲学家 p 右边的叉子用 `right(p)` 表示；其中的取模运算处理了最后一位哲学家（p=4）想拿右边叉子的情况，那正是 0 号叉子。

我们还需要一些信号量来解决这个问题。假设我们有五个，每把叉子一个：`sem_t forks[5]`。

### 一个错误的解法

我们来尝试第一个解法。假设把每个信号量（在 `forks` 数组中）都初始化为 1，也假设每位哲学家都知道自己的编号（p）。于是可以写出 `get_forks()` 和 `put_forks()`（图 31.15）。

这个（错误的）解法背后的直觉是这样：要拿叉子，我们只需给每把叉子加个“锁”——先左边那把，再右边那把。吃完饭再释放。很简单，对吧？不幸的是，在这个例子里，简单就意味着错误。你能看出问题出在哪吗？想一想。

<figure class="book-figure">
<img src="/figures/31-f07.png" alt="Figure 31.16" loading="lazy">
<figcaption><span class="fig-label">图 31.16</span>在 get_forks() 中打破依赖</figcaption>
</figure>

问题就是死锁。如果每位哲学家都恰好在别人拿右边叉子之前先拿到了自己左边的叉子，那么每个人都会抓住一把叉子、永远等着另一把。具体来说，哲学家 0 拿到 0 号叉，哲学家 1 拿到 1 号叉，哲学家 2 拿到 2 号叉，哲学家 3 拿到 3 号叉，哲学家 4 拿到 4 号叉；所有叉子都被拿走了，而所有哲学家都在等别人手里的叉子。我们很快就会更详细地研究死锁；眼下可以确定地说，这不是一个可行的解法。

### 一个解法：打破依赖

对付这个问题最简单的办法，是改变至少一位哲学家拿叉子的方式；事实上 Dijkstra 本人就是这么解决的。具体来说，假设哲学家 4（编号最大的那位）与其他人的拿取顺序不同（图 31.16）；`put_forks()` 的代码保持不变。

因为最后一位哲学家先拿右边再拿左边，就不会出现每位哲学家都拿着一把叉子、苦等另一把的局面；等待的环被打破了。想一想这个解法带来的影响，说服自己它是可行的。

还有别的一些类似的“著名”问题，比如抽烟者问题、睡眠理发师问题。它们大多只是给你一个思考并发的借口，有些名字还挺有意思。想了解更多，或者只是想多练练并发思维，可以去查一查 [D08]。

## 31.7 线程节流

信号量偶尔还有另一种简单用法，这里也介绍一下。具体问题是：程序员怎样才能阻止“过多”线程同时做某件事、把系统拖垮？答案是：为“过多”定一个阈值，然后用一个信号量限制同时执行那段代码的线程数。我们把这种做法称为**节流**（throttling）[T99]，并把它看作一种准入控制。

考虑一个更具体的例子。设想你创建了几百个线程并行处理某个问题。可是在代码的某一部分，每个线程都要申请一大块内存来完成部分计算；我们把这部分代码叫做内存密集型区域。如果所有线程同时进入这个区域，所有内存分配请求加起来就会超过机器的物理内存总量。结果机器开始频繁换页（也就是在磁盘和内存之间来回换入换出页面），整个计算慢得像爬。

一个简单的信号量就能解决这个问题。把信号量的值初始化为你希望同时进入内存密集型区域的最大线程数，然后在这段区域前后加上 `sem_wait()` 和 `sem_post()`，信号量就能自然而然地限制同时待在这段危险代码里的线程数。

## 31.9 小结

信号量是编写并发程序时强大而灵活的原语。有些程序员因为它们简单好用而只用它们，不用锁和条件变量。

本章只介绍了几类经典问题及其解法。如果你想知道更多，还有很多资料可以参考。一个很好（而且免费）的参考资料是 Allen Downey 关于并发与信号量编程的书 [D08]。书里有很多练习题，你可以动手做，以加深对信号量这一具体主题、以及并发这一普遍主题的理解。成为真正的并发专家需要多年努力；在课堂所学之外继续深入，无疑是掌握这门主题的关键。

::: tip 小心泛化

由此可见，泛化这种抽象技巧在系统设计中相当有用：一个好想法可以稍微拓宽一点，从而解决更大一类问题。不过泛化时要小心；正如 Lampson 提醒我们的：“不要泛化；泛化通常都是错的”[L83]。人们可以把信号量看作锁和条件变量的泛化；可是这样的泛化有必要吗？而且，考虑到在信号量之上实现条件变量的难度，这种泛化也许并不像你想的那么“通用”。

:::

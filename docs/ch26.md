# 第 26 章　并发：介绍

<div class="chap-en">Concurrency: An Introduction</div>

到目前为止，我们已经看到了操作系统所提供的基本抽象是如何发展出来的。我们看到了如何把单个物理 CPU 变成多个虚拟 CPU，从而营造出多个程序同时在运行的假象。我们也看到了如何为每个进程营造出一个又大又私有的虚拟内存；地址空间这一抽象让每个程序都以为自己独占内存，而实际上操作系统正悄悄地把多个地址空间多路复用到物理内存（有时还有磁盘）之上。

在本章中，我们为一个正在运行的进程引入一个新的抽象：线程。过去我们认为一个程序只有一个执行点（即只有一个 PC，指令从那里取出并执行）；而在多线程程序中，执行点不止一个（即多个 PC，各自取指、各自执行）。换一种理解方式：每个线程都很像一个独立的进程，只有一点不同——它们共享同一个地址空间，因此可以访问同一份数据。

因此，单个线程的状态与进程的状态非常相似。它有一个程序计数器（PC），用来跟踪程序当前从哪里取指令。每个线程都有自己私有的寄存器集合，用于计算；所以，如果有两个线程在同一个处理器上运行，从运行其中一个（T1）切换到运行另一个（T2）时，就必须进行一次上下文切换。线程之间的上下文切换与进程之间的上下文切换相当类似：必须保存 T1 的寄存器状态，并在运行 T2 之前恢复 T2 的寄存器状态。对于进程，我们把状态保存到进程控制块（PCB）中；现在，我们需要一个或多个线程控制块（TCB）来保存进程中每个线程的状态。不过，线程之间与进程之间的上下文切换有一个重要区别：地址空间保持不变（也就是说，不必切换当前使用的页表）。

线程与进程的另一个重要区别在于栈。在经典进程地址空间的简单模型中（现在可以称之为单线程进程），只有一个栈，通常位于地址空间的底部（图 26.1，左）。

然而，在多线程进程中，每个线程都独立运行，自然也可能调用各种例程来完成自己的工作。于是地址空间里不再只有一个栈，而是每个线程一个栈。假设我们的多线程进程里有两个线程，得到的地址空间就大不相同了（图 26.1，右）。

在这张图里可以看到两个栈散布在进程的地址空间中。因此，任何分配在栈上的变量、参数、返回值以及其他放在栈上的东西，都会被放进所谓的线程局部存储（thread-local storage），也就是相应线程自己的栈。

你或许还会注意到，这破坏了我们原本漂亮的地址空间布局。以前栈和堆可以各自独立增长，只有当地址空间用完时才会出问题。而现在这种好事没有了。好在通常问题不大，因为栈一般不需要很大（大量使用递归的程序除外）。

## 26.1 为什么要用线程？

在深入线程的细节、以及编写多线程程序可能遇到的各种麻烦之前，我们先回答一个更简单的问题：到底为什么要用线程？

事实证明，至少有两个主要理由值得使用线程。第一个很简单：并行（parallelism）。设想你在写一个对超大数组做运算的程序，比如把两个大数组相加，或者把数组中每个元素的值都增加若干。如果只在单个处理器上运行，任务很直接：挨个做完就行。但如果你在多处理器的系统上执行这个程序，就有可能让每个处理器各承担一部分工作，从而大幅加速。把标准的单线程程序改造成能在多个 CPU 上分担工作的程序，这一过程称为并行化（parallelization）；而为每个 CPU 分配一个线程来干活，是在现代硬件上让程序跑得更快的自然且典型的做法。

第二个理由稍微微妙一些：避免因为慢速 I/O 而阻塞程序的推进。设想你在写一个执行各类 I/O 的程序：等待发送或接收消息、等待一次显式的磁盘 I/O 完成，甚至（隐式地）等待一次缺页异常处理结束。与其干等，程序也许想做点别的事，比如利用 CPU 做计算，或者发起更多 I/O 请求。用线程是避免卡住的自然办法：当一个线程在等待（即阻塞在 I/O 上）时，CPU 调度器可以切换到其他就绪的线程，让它们做点有用的事。线程让单个程序内部的 I/O 与其他活动得以重叠，这很像多道程序（multiprogramming）在多个程序之间对进程所做的那样；因此，许多现代服务器端应用（Web 服务器、数据库管理系统之类）在实现中都使用了线程。

当然，在上述两种情形下，你也可以用多个进程代替线程。但线程共享地址空间，因此共享数据很方便，在构建这类程序时是自然的选择。对于逻辑上相互独立、内存中几乎不需要共享数据结构的任务，进程则是更稳妥的选择。

## 26.3 为什么更糟：共享数据

上面那个简单的线程例子很好地演示了线程如何创建，以及它们如何按照调度器的决定以不同顺序运行。不过，它没有展示线程在访问共享数据时是如何相互影响的。

让我们设想一个简单的例子：两个线程都想更新一个全局共享变量。我们要研究的代码见图 26.6。

关于这段代码有几点说明。第一，按照 Stevens 的建议 [SR05]，我们把线程创建和等待的例程包装了一下，一旦失败就直接退出；对于这么简单的程序，我们至少希望知道出错了（如果确实出错的话），而不必做多聪明的处理（直接退出就行）。因此，`Pthread_create()` 只是调用 `pthread_create()` 并确认返回码为 0；如果不为 0，就打印一条消息并退出。

第二，两个工作线程没有各写一份独立的函数体，而是共用同一段代码，并通过参数（这里是一个字符串）把要做的事告诉线程，这样每个线程在输出消息前可以打印不同的字母。

最后，也是最重要的，现在我们来看看每个工作线程想干什么：往共享变量 `counter` 上加一个数，并且在循环里做一千万次（`1e7`）。因此，期望的最终结果是：20,000,000。

现在我们编译并运行这个程序，看看它的表现。有时候，一切都如我们所愿：

```c
prompt> gcc -o main main.c -Wall -pthread; ./main
main: begin (counter = 0)
A: begin
B: begin
A: done
B: done
main: done with both (counter = 20000000)
```

```c
#include <stdio.h>
#include <pthread.h>
#include "common.h"
#include "common_threads.h"

static volatile int counter = 0;

// mythread()
//
// 只是在一个循环里反复把 counter 加 1
// 当然，没有人会真的这样把 1000 万
// 加到计数器上，但它把问题暴露得很清楚。
//
void *mythread(void *arg) {
    printf("%s: begin\n", (char *) arg);
    int i;
    for (i = 0; i < 1e7; i++) {
        counter = counter + 1;
    }
    printf("%s: done\n", (char *) arg);
    return NULL;
}

// main()
//
// 只启动两个线程（pthread_create）
// 然后等待它们结束（pthread_join）
//
int main(int argc, char *argv[]) {
    pthread_t p1, p2;
    printf("main: begin (counter = %d)\n", counter);
    Pthread_create(&p1, NULL, mythread, "A");
    Pthread_create(&p2, NULL, mythread, "B");

    // join 等待线程结束
    Pthread_join(p1, NULL);
    Pthread_join(p2, NULL);
    printf("main: done with both (counter = %d)\n",
            counter);
    return 0;
}
```

## 26.4 问题的核心：不受控的调度

要理解为什么会这样，必须弄懂编译器为更新 `counter` 生成的是什么代码序列。这里我们只想给 `counter` 加 1。于是，完成这件事的代码序列在 x86 上大致是这样的：

```c
mov    0x8049a1c, %eax
add    $0x1, %eax
mov    %eax, 0x8049a1c
```

这个例子假设变量 `counter` 位于地址 `0x8049a1c`。在这三条指令的序列中，先用 x86 的 `mov` 指令取出该地址上的内存值放进 `eax` 寄存器；然后执行 `add`，把 1（`0x1`）加到 `eax` 的内容上；最后，把 `eax` 的内容存回同一地址的内存。

设想两个线程之一（线程 1）进入了这段代码，即将把 `counter` 加一。它把 `counter` 的值（假定初始是 50）装入自己的 `eax` 寄存器，于是线程 1 的 `eax=50`。然后它给寄存器加一，`eax=51`。就在这时，不幸的事发生了：一个定时器中断到来，操作系统于是把当前运行线程的状态（它的 PC、包括 `eax` 在内的各个寄存器等）保存到该线程的 TCB 中。

接着更糟的事发生了：线程 2 被选中运行，它也进入了同一段代码。它同样执行第一条指令，取到 `counter` 的值放进自己的 `eax`（记住：每个线程运行时都有自己私有的寄存器；这些寄存器由上下文切换代码保存和恢复，相当于被虚拟化了）。此时 `counter` 的值仍是 50，于是线程 2 的 `eax=50`。再假设线程 2 执行了接下来的两条指令，把 `eax` 加一（`eax=51`），然后把 `eax` 的内容存回 `counter`（地址 `0x8049a1c`）。于是全局变量 `counter` 现在的值是 51。

最后，又发生了一次上下文切换，线程 1 恢复运行。回想一下，它刚刚执行完 `mov` 和 `add`，现在正要执行最后那条 `mov` 指令。也别忘了此时 `eax=51`。于是最后这条 `mov` 执行，把值写回内存；`counter` 又被设成了 51。

简单地说，刚刚发生的事情是：给 `counter` 加一的代码执行了两次，但 `counter` 从 50 出发，如今只等于 51。这个程序的“正确”版本本应让 `counter` 等于 52。

让我们看一段详细的执行轨迹，以便更好地理解问题所在。假设在本例中，上面的代码被加载到内存地址 100 处，如下面的序列所示（给那些习惯漂亮的类 RISC 指令集的人提个醒：x86 的指令是变长的，这条 `mov` 指令占 5 字节内存，`add` 只占 3 字节）：


有了这些假设，发生的事情就如图 26.7 所示。假定 `counter` 的初值是 50，请顺着这个例子自己走一遍，确认你真的弄清了来龙去脉。

我们在此演示的现象叫做竞态条件（race condition），更具体地说，是数据竞态（data race）：结果取决于代码执行的时间顺序。运气不好时（即上下文切换发生在执行过程中不合时宜的位置），我们就会得到错误的结果。事实上，每次的结果都可能不同；于是我们不再得到那种漂亮的确定性计算（这是我们对计算机习以为常的期待），而把这种结果称为不确定的（indeterminate）：无法预知输出是什么，而且很可能每次运行都不一样。

由于多个线程执行这段代码可能导致竞态条件，我们把这段代码称为临界区（critical section）。临界区是指访问共享变量（更一般地说，共享资源）的一段代码，它绝不能被多于一个线程并发执行。

对于这段代码，我们真正想要的是所谓的互斥（mutual exclusion）。这一性质保证：如果一个线程正在临界区内执行，其他线程就会被阻止进入。

顺便说一句，几乎所有这些术语都是 Edsger Dijkstra 创造的。他是这个领域的先驱，正是凭这项工作以及其他工作获得了图灵奖；他在 1968 年关于“协作的顺序进程”（Cooperating Sequential Processes）的论文 [D68] 中对这个问题做了极其清晰的描述。在本书这一部分，我们还会多次听到 Dijkstra 的名字。

::: tip 使用原子操作

原子操作是构建计算机系统时最强大的底层技术之一，从计算机体系结构，到并发代码（我们正在学的），到文件系统（很快也会学到），到数据库管理系统，甚至分布式系统 [L+93]，都能见到它的身影。把一系列动作变成原子操作，其思想可以用“全有或全无”（all or nothing）这句话来概括：要么看起来你希望归为一组的全部动作都发生了，要么一个都没发生，看不到任何中间状态。有时，把许多动作归并成一个原子动作被称为事务（transaction），这一思想在数据库和事务处理领域得到了充分发展 [GR92]。在我们探索并发的主题中，会使用同步原语把一小段指令序列变成原子的执行块，但原子性的概念远不止于此，我们将会看到。例如，文件系统使用日志（journaling）或写时复制（copy-on-write）之类的技术，来原子地转换其磁盘上的状态——这对于在系统故障面前保持正确运行至关重要。如果现在看不懂，别担心——在后面的某一章里你会明白的。

:::

## 26.5 对原子性的渴望

解决这个问题的一种办法，是提供更强大的指令，一步就完成我们需要的全部操作，从而消除中断不合时宜地到来的可能性。例如，如果我们有这样一条超级指令：

```c
memory-add 0x8049a1c, $0x1
```

假设这条指令把某个值加到某个内存位置，并且硬件保证它原子地执行；那么当这条指令执行时，就会如我们所愿地完成更新。它不可能在执行中途被打断，因为这正是硬件给我们的保证：当中断发生时，指令要么根本没执行，要么已经执行完毕；不存在中间状态。硬件可以很美好，不是吗？

在这个语境下，原子（atomically）的意思是“作为一个整体”，有时我们也把它理解为“全有或全无”。我们希望的是把这三条指令的序列原子地执行：

```c
mov    0x8049a1c, %eax
add    $0x1, %eax
mov    %eax, 0x8049a1c
```

如前所述，如果真有一条指令能完成这件事，我们只要发出这条指令就完事了。但在一般情况下，我们不会有这样的指令。设想我们正在构建一棵并发 B 树，想要更新它；难道我们真的希望硬件支持一条“原子更新 B 树”的指令吗？恐怕不会，至少在一个正常的指令集里不会。

因此，我们转而向硬件要几条有用的指令，在它们之上构建一套通用的东西，也就是所谓的同步原语（synchronization primitives）。借助这些硬件支持，再加上操作系统的一些帮助，我们就能编写多线程代码，以同步、受控的方式访问临界区，从而在并发执行的重重挑战之下依然可靠地得到正确结果。相当了不起，对吧？

这就是本书这一部分要研究的问题。这是一个美妙而艰难的问题，应该会让你的脑袋有点疼。如果不疼，说明你还没弄懂！继续琢磨，直到头疼为止；那时你就知道自己走在正确的路上了。到那时候，休息一下；我们可不希望你的头太疼。

## 26.6 还有一个问题：等待另一个线程

本章把并发问题设定成线程之间似乎只有一种交互：访问共享变量，以及临界区对原子性的需求。事实证明，还有一种常见的交互会出现：一个线程必须等另一个线程完成某个动作之后才能继续。举例来说，当一个进程执行磁盘 I/O 并被置为睡眠时，就会出现这种交互；I/O 完成后，这个进程需要被唤醒，才能继续运行。

因此，在接下来的几章里，我们不仅要研究如何构建支持原子性的同步原语，还要研究支持多线程程序中常见的这种睡眠／唤醒交互的机制。如果现在还不明白，没关系！读到条件变量那一章时，你会明白的。如果到那时候还不明白，那就不太好了，你应该把那一章再读一遍（再读一遍），直到明白为止。

::: aside 关键的并发术语

**临界区、竞态条件、不确定、互斥** 这四个术语对并发代码如此核心，我们认为值得专门把它们点出来。更多细节可以参阅 Dijkstra 的早期工作 [D65,D68]。

- 临界区（critical section）是访问共享资源（通常是变量或数据结构）的一段代码。
- 如果多个执行线程几乎同时进入临界区，两者都试图更新共享数据结构，就会产生竞态条件（race condition，或数据竞态 [NM92]），导致令人意外（也许还不想要）的结果。
- 由一处或多处竞态条件构成的程序是不确定的（indeterminate）程序：它的输出随运行而变，取决于哪些线程在什么时候运行。因此结果不具有确定性，而确定性通常是我们对计算机系统的期待。
- 为了避免这些问题，线程应当使用某种互斥原语；这样做能保证任一时刻只有一个线程进入临界区，从而避免竞态，让程序输出恢复确定性。

:::

## 26.7 小结：为什么要在操作系统课里讲？

在收尾之前，你可能会有一个疑问：为什么要在操作系统课里学这个？“历史”就是一句话的答案：操作系统是最早的并发程序，许多技术最初就是为了在操作系统内部使用而发明的。后来有了多线程进程，应用程序员也不得不考虑这些事情了。

举个例子，设想有两个进程在运行。假设它们都调用 `write()` 往文件里写数据，并且都希望把数据追加到文件末尾（即把数据加在文件尾部，从而增加文件长度）。为了做到这一点，两者都必须分配一个新的块，在文件的 inode 中记录这个块的位置，并修改文件大小以反映新的更大尺寸（还有其他一些事；我们会在本书第三部分学习更多关于文件的知识）。由于中断可能随时到来，更新这些共享结构（例如用于分配的位图，或文件的 inode）的代码就是临界区；因此，从引入中断的最初时刻起，操作系统设计者就必须操心操作系统如何更新内部结构。一次不合时宜的中断会引发前面描述的所有问题。毫不奇怪，页表、进程列表、文件系统结构，以及几乎每一个内核数据结构，都必须借助恰当的同步原语小心访问，才能正确工作。

## 作业（模拟）

这个程序 `x86.py` 让你看到不同的线程交错方式如何导致或避免竞态条件。程序如何工作，详见 README，然后回答下面的问题。

### 问题

1. 我们来研究一个简单的程序 `loop.s`。先读懂它，然后用这些参数运行：`./x86.py -t 1 -p loop.s -i 100 -R dx`。这指定了一个线程、每 100 条指令发生一次中断，并跟踪寄存器 `%dx`。运行过程中 `%dx` 的值会是多少？用 `-c` 选项来核对答案；左侧显示的是右侧指令执行完之后寄存器（或内存）的值。
2. 同样的代码，不同的选项：`./x86.py -p loop.s -t 2 -i 100 -a dx=3,dx=3 -R dx`。这里指定了两个线程，并把每个 `%dx` 都初始化为 3。`%dx` 会取到哪些值？用 `-c` 运行核对。多个线程的存在会影响你的推算吗？这段代码里存在竞态吗？
3. 运行这个：`./x86.py -p loop.s -t 2 -i 3 -r -R dx -a dx=3,dx=3`。它让中断间隔变得很小且随机；用不同的随机种子（`-s`）观察不同的交错方式。中断频率会改变什么吗？
4. 现在换一个程序 `looping-race-nolock.s`，它访问位于地址 2000 的一个共享变量，我们把这个变量叫做 `value`。先用单个线程运行，确认你的理解：`./x86.py -p looping-race-nolock.s -t 1 -M 2000`。整个运行过程中 `value`（即内存地址 2000 处）的值是多少？用 `-c` 核对。
5. 用多轮循环／多线程运行：`./x86.py -p looping-race-nolock.s -t 2 -a bx=3 -M 2000`。为什么每个线程循环三次？`value` 的最终值是多少？
6. 用随机的中断间隔运行：`./x86.py -p looping-race-nolock.s -t 2 -M 2000 -i 4 -r -s 0`，并换用不同的种子（`-s 1`、`-s 2` 等）。你能只看线程交错就判断出 `value` 的最终值吗？中断的时机有影响吗？中断可以在哪里安全地发生？哪里不行？换句话说，临界区究竟在哪儿？
7. 现在研究固定的中断间隔：`./x86.py -p looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 1`。共享变量 `value` 的最终值会是多少？改成 `-i 2`、`-i 3` 等等又会怎样？哪些中断间隔下程序给出的答案是“正确”的？
8. 用更多的循环做同样的实验（例如设置 `-a bx=100`）。哪些中断间隔（`-i`）能带来正确的结果？哪些间隔的结果出人意料？
9. 最后一个程序 `wait-for-me.s`。运行：`./x86.py -p wait-for-me.s -a ax=1,ax=0 -R ax -M 2000`。这会把线程 0 的 `%ax` 设为 1、线程 1 的 `%ax` 设为 0，并观察 `%ax` 和内存位置 2000。这段代码应该怎样表现？两个线程如何使用位置 2000 处的值？它的最终值会是多少？
10. 现在把输入对调：`./x86.py -p wait-for-me.s -a ax=0,ax=1 -R ax -M 2000`。两个线程的表现如何？线程 0 在干什么？改变中断间隔（例如 `-i 1000`，或者改用随机间隔）会怎样改变轨迹的结果？这个程序高效地利用了 CPU 吗？

# 第 29 章　基于锁的并发数据结构

<div class="chap-en">Lock-based Concurrent Data Structures</div>

在告别锁之前，我们先来看看怎样在一些常见的数据结构里使用锁。给数据结构加上锁，使它能够被多个线程使用，这个结构就成为**线程安全**（thread safe）的了。当然，究竟怎样加锁，同时决定了这个数据结构的正确性和性能。于是，我们的挑战是：

::: crux 如何给数据结构加锁

给定某个数据结构，我们应该怎样给它加锁，才能让它正确工作？进一步说，怎样加锁才能让这个数据结构具备高性能，使许多线程能够同时（也就是并发地）访问它？
:::

当然，要把所有数据结构、所有提高并发度的方法都讲一遍是不现实的：这个题目已经研究了很多年，（毫不夸张地说）发表了成千上万篇研究论文。因此，我们只希望能提供足够的入门材料，让你了解其中所需的思维方式，并推荐一些好的资料来源，供你自己进一步钻研。我们认为 Moir 和 Shavit 的综述是极好的信息来源 [MS04]。

这个并发计数器很简单，也能正确工作。事实上，它遵循了一种最简单的并发数据结构常用的设计模式：仅仅加一把锁，在调用操作该数据结构的例程时获取锁，从调用返回时释放锁。这样一来，它就很像用管程（monitor）[BH73] 构建的数据结构——在那种结构里，锁随着对象方法的调用和返回自动获取和释放。

到这里，你已经有了一个能用的并发数据结构。可能存在的问题是性能。如果你的数据结构太慢，光加一把锁就不够了，还得做更多的事；这类优化（如果需要的话）正是本章余下部分要讨论的内容。注意，如果数据结构并不算慢，那你已经完工了！简单的办法能奏效，就不必搞什么花哨的东西。

为了弄清这种简单做法在性能上的代价，我们跑了一个基准测试：每个线程把同一个共享计数器更新固定次数，然后改变线程数量。图 29.5 给出了 1 到 4 个线程活动时的总耗时，每个线程都更新计数器 100 万次。这个实验在一台配有四个 Intel 2.7 GHz i5 CPU 的 iMac 上运行；我们期望活动的 CPU 越多，单位时间内完成的总工作量就越大。

从图中最上面那条线（标为 "Precise"，精确）可以看出，这个同步计数器的可扩展性很差。单个线程完成 100 万次计数器更新只需极短的时间（大约 0.03 秒），而让两个线程各自并发地更新计数器 100 万次，速度却急剧下降（花了 5 秒多！）。线程再多只会更糟。

理想情况下，你希望多个处理器上运行的线程完成得和单个处理器上的单个线程一样快。达到这个目标就叫**完美扩展**（perfect scaling）：尽管完成的工作更多，但它们是并行完成的，因此完成任务所需的时间并没有增加。

**可扩展的计数**

令人惊讶的是，研究者们多年来一直在研究如何构建可扩展性更好的计数器 [MS04]。更令人惊讶的是，可扩展的计数确实很重要，操作系统性能分析方面的近期工作已经表明了这一点 [B+10]：如果没有可扩展的计数，一些运行在 Linux 上的工作负载在多核机器上会遭遇严重的可扩展性问题。

为解决这个问题，人们发展出许多技术。这里介绍其中一种，称为**近似计数器**（approximate counter）[C06]。

近似计数器的做法是：用一个全局计数器，再加上许多局部物理计数器（每个 CPU 核一个），共同表示一个逻辑计数器。具体来说，在有 4 个 CPU 的机器上，有 4 个局部计数器和一个全局计数器。除了这些计数器，还有锁：每个局部计数器一把¹，全局计数器一把。

<figure class="book-figure">
<img src="/figures/29-f03.png" alt="Figure 29.3" loading="lazy">
<figcaption><span class="fig-label">图 29.3</span>追踪近似计数器</figcaption>
</figure>

近似计数的基本思想如下。当运行在某个核上的线程想要增加计数时，它就增加自己的局部计数器；对这个局部计数器的访问由相应的局部锁来同步。因为每个 CPU 都有自己的局部计数器，不同 CPU 上的线程可以无争用地更新各自的局部计数器，所以对计数器的更新是可扩展的。

不过，为了让全局计数器保持最新（以防某个线程想读取它的值），局部值会周期性地转移给全局计数器：先获取全局锁，把全局计数器加上该局部计数器的值，然后把局部计数器清零。

这种从局部到全局的转移多久发生一次，由一个阈值 S 决定。S 越小，计数器的行为就越像前面那个不可扩展的计数器；S 越大，计数器的可扩展性越好，但全局值可能与实际计数相差越远。当然，也可以干脆把所有局部锁和全局锁都获取一遍（按指定的顺序，以避免死锁），从而得到精确的值，但那样就不可扩展了。

为了说得更清楚，看一个例子（图 29.3）。这个例子里阈值 S 设为 5，4 个 CPU 上各有一个线程在更新自己的局部计数器 L1 …… L4。跟踪记录里还给出了全局计数器的值（G），时间自上而下推进。每个时间步，某个局部计数器可能被增加；一旦局部值达到阈值 S，这个局部值就被转移到全局计数器，同时局部计数器被清零。

图 29.5 中下面那条线（标为 "Approximate"，近似）给出了阈值 S 取 1024 时近似计数器的性能。性能非常出色：在 4 个处理器上把计数器更新 400 万次所用的时间，几乎不比在 1 个处理器上更新 100 万次更多。

```c
typedef struct __counter_t {
global;
// 全局计数
pthread_mutex_t glock;
// 全局锁
local[NUMCPUS]; // 每 CPU 计数
pthread_mutex_t llock[NUMCPUS]; // ... and locks
threshold;
// 更新频率
} counter_t;
// 初始化：记录阈值、初始化锁与各项数值
of all local counts and global count
void init(counter_t *c, int threshold) {
c->threshold = threshold;
c->global = 0;
pthread_mutex_init(&c->glock, NULL);
int i;
for (i = 0; i < NUMCPUS; i++) {
c->local[i] = 0;
pthread_mutex_init(&c->llock[i], NULL);
// update：通常只需拿本地锁并更新
// 本地计数；一旦它超过阈值，
// 获取全局锁，把本地值累加到全局
void update(counter_t *c, int threadID, int amt) {
int cpu = threadID % NUMCPUS;
pthread_mutex_lock(&c->llock[cpu]);
c->local[cpu] += amt;
if (c->local[cpu] >= c->threshold) {
// 累加到全局（假定 amt>0）
pthread_mutex_lock(&c->glock);
c->global += c->local[cpu];
pthread_mutex_unlock(&c->glock);
c->local[cpu] = 0;
pthread_mutex_unlock(&c->llock[cpu]);
// get：直接返回全局值（近似）
int get(counter_t *c) {
pthread_mutex_lock(&c->glock);
int val = c->global;
pthread_mutex_unlock(&c->glock);
return val; // 只是近似值！
```

图 29.6 展示了阈值 S 的重要性：4 个线程在 4 个 CPU 上各自把计数器增加 100 万次。如果 S 很小，性能就差（但全局计数始终相当准确）；如果 S 很大，性能极佳，但全局计数会滞后（最多滞后 CPU 数量乘以 S）。近似计数器带来的正是这种精度与性能之间的权衡。

::: tip 更多并发未必更快

如果你设计的方案引入了大量额外开销（比如频繁地获取和释放锁，而不是只做一次），那么"并发度更高"这件事可能并不重要。简单的方案往往效果不错，尤其是很少用到那些昂贵操作的时候。加更多的锁、增加复杂度，反而可能害了你。话虽如此，有一个办法能真正弄清高下：把两种方案（简单但并发度低、复杂但并发度高）都实现出来，测量它们各自的表现。归根到底，性能上做不了假——你的想法要么更快，要么不快。
:::

## 29.2 并发链表

接下来研究一个更复杂的数据结构：链表。我们还是从基本做法开始。为简单起见，这里省略这种链表显然会有的一些例程，只关注并发的插入（insert）和查找（lookup）；删除（delete）之类就留给读者自己琢磨了。图 29.7 给出了这个初级数据结构的代码。

从代码里可以看到，插入例程在入口处获取锁，在出口处释放锁。有一个小小的麻烦：如果 `malloc()` 恰好失败（这种情况很少见），代码在让插入失败之前还必须释放锁。

这种异常的控制流已经被证明很容易出错；最近一项对 Linux 内核补丁的研究发现，很大一部分 bug（接近 40%）出现在这类很少被执行到的代码路径上（事实上，这一观察启发了我们自己的一项研究：我们把某个 Linux 文件系统里所有因内存分配失败而走的路径都去掉了，结果得到一个更健壮的系统 [S+11]）。

于是就有了一个挑战：我们能否重写 insert 和 lookup 两个例程，使它们在并发插入下仍然正确，同时又避免出现"失败路径也必须加上 unlock 调用"的情况？

这一次答案是肯定的。具体做法是把代码结构调整一下：插入代码里，让加锁和解锁只包住真正的临界区；查找代码里，改用统一的出口路径。前者之所以可行，是因为插入的一部分工作其实并不需要加锁：假设 `malloc()` 本身是线程安全的，每个线程都可以放心调用它，不必担心竞态条件或其他并发 bug，只有在更新共享链表时才需要持锁。这些修改的细节见图 29.8。

至于查找例程，只需做一处简单的代码改写：从主搜索循环里跳到一个统一的返回路径。这样做同样减少了代码中获取/释放锁的位置，从而降低了无意中引入 bug（比如返回前忘了解锁）的可能性。


**链表的扩展**

虽然我们又一次得到了一个基本的并发链表，但情况依旧是：它的可扩展性并不好。研究者们探索过一种能在链表内部实现更多并发的技术，叫做交接锁（hand-over-hand locking，也叫锁耦合，lock coupling）[MS04]。

思路相当简单。与其为整个链表设一把锁，不如给链表里的每个节点都加一把锁。遍历链表时，代码先获取下一个节点的锁，再释放当前节点的锁（这个名字正来源于此：像双手交替攀绳一样，一把接一把）。

::: tip 当心锁与控制流

有一条通用的设计建议，对并发代码和其他代码都适用：要提防那些会导致函数返回、退出或其他类似错误情况、从而中断函数执行的控制流变化。因为很多函数在开头会获取锁、分配内存或做其他类似的有状态操作，一旦出错，代码必须在返回前把这些状态全部撤销，这很容易出错。因此，最好在组织代码时尽量减少这种模式。
:::

从概念上说，交接锁链表是有道理的，它能让链表操作达到很高的并发度。然而在实践中，很难让这种结构比简单的单锁方案更快，因为遍历时为每个节点获取和释放锁的开销实在太高。即使链表非常大、线程非常多，允许多个遍历同时进行所带来的并发度，也不太可能胜过"抓一把锁、做个操作、放开锁"的做法。也许某种混合方案（比如每经过若干个节点才抓一把新锁）值得研究一下。

## 29.3 并发队列

到现在你应该已经知道，把数据结构变成并发的总有一个标准办法：加一把大锁。对队列我们就不讲这个办法了，相信你能自己搞定。

我们来看看 Michael 和 Scott 设计的一种并发度稍高的队列 [MS98]。这个队列用到的数据结构和代码见图 29.9。

仔细研究这段代码你会发现，其中有两把锁：一把给队头，一把给队尾。这两把锁的目的是让入队（enqueue）和出队（dequeue）操作能够并发进行。通常情况下，入队例程只访问队尾锁，出队只访问队头锁。

Michael 和 Scott 用到的一个技巧是增加一个哑节点（在队列初始化代码里分配）；正是这个哑节点把队头操作和队尾操作分开了。研究一下这段代码，更好的是把它敲进去、跑起来、测一测，以便深入理解它的工作方式。

队列在多线程应用里用得很多。不过这里这种（只用锁的）队列往往不能完全满足这类程序的需要。下一章讲条件变量时，我们会深入研究一种更完善的有界队列（bounded queue），它能让线程在队列为空或过满时等待。敬请期待！

```c
typedef struct __node_t {
value;
struct __node_t
*next;
} node_t;
typedef struct __queue_t {
node_t
*head;
node_t
*tail;
pthread_mutex_t
head_lock, tail_lock;
} queue_t;
void Queue_Init(queue_t *q) {
node_t *tmp = malloc(sizeof(node_t));
tmp->next = NULL;
q->head = q->tail = tmp;
pthread_mutex_init(&q->head_lock, NULL);
pthread_mutex_init(&q->tail_lock, NULL);
void Queue_Enqueue(queue_t *q, int value) {
node_t *tmp = malloc(sizeof(node_t));
assert(tmp != NULL);
tmp->value = value;
tmp->next
= NULL;
pthread_mutex_lock(&q->tail_lock);
q->tail->next = tmp;
q->tail = tmp;
pthread_mutex_unlock(&q->tail_lock);
int Queue_Dequeue(queue_t *q, int *value) {
pthread_mutex_lock(&q->head_lock);
node_t *tmp = q->head;
node_t *new_head = tmp->next;
if (new_head == NULL) {
pthread_mutex_unlock(&q->head_lock);
return -1; // 队列原本为空
*value = new_head->value;
q->head = new_head;
pthread_mutex_unlock(&q->head_lock);
free(tmp);
return 0;
```

## 29.4 并发哈希表

最后讨论一种简单而且用途广泛的并发数据结构：哈希表。我们只关注不做扩容的简单哈希表；处理扩容还需要多做一些工作，这部分留作读者的练习（抱歉！）。

这个并发哈希表（图 29.10）直截了当，是用前面开发的并发链表构建的，效果出奇地好。它性能好的原因在于：它没有为整个结构设一把锁，而是每个哈希桶（hash bucket）一把锁（每个桶由一个链表表示）。这样一来，许多操作就能并发进行。

图 29.11 给出了哈希表在并发更新下的性能（4 个线程各做 1 万到 5 万次并发更新，仍然是在那台有 4 个 CPU 的 iMac 上）。作为对比，图中还给出了（单锁）链表的性能。从图上可以看出，这个简单的并发哈希表扩展得极好；相比之下，链表就不行了。

## 29.5 小结

我们介绍了几种有代表性的并发数据结构：从计数器，到链表和队列，最后到无处不在、使用极广的哈希表。一路走来，我们学到了几条重要的经验：在控制流变化处获取和释放锁时要格外小心；提高并发度并不一定提升性能；只有性能问题真的出现了，才应该去解决它。最后这一点，也就是避免过早优化，对任何在意性能的开发者都至关重要；如果让某个东西变快并不能改善应用的整体性能，那这么做就毫无价值。

::: tip 避免过早优化（Knuth 定律）

构建并发数据结构时，先采用最基本的方法：加一把大锁来提供同步访问。这样做出来的结构很可能是正确的；如果之后发现它有性能问题，再加以改进，也就是只在必要时才让它变快。正如 Knuth 的名言："过早优化是万恶之源。"

许多操作系统在最初转向多处理器时都只用一把锁，其中包括 Sun OS 和 Linux。在后者的内核里，这把锁甚至有个名字：大内核锁（big kernel lock，BKL）。很多年里，这种简单做法都还不错，但当多 CPU 系统成为常态后，"内核中同时只允许一个线程活动"就成了性能瓶颈。于是，终于到了给这些系统加上"提高并发度"这项优化的时候了。在 Linux 里，采取的是比较直接的做法：把一把锁换成许多把。在 Sun，则做出了更激进的决定：干脆从头构建一个全新的操作系统，也就是 Solaris，让并发从第一天起就融入其根本设计。想了解这些迷人的系统，可以读读讲 Linux 和 Solaris 内核的书 [BC05, MM00]。
:::

作业（代码）

这次作业中，你将练习编写并发代码并测量其性能。学会写出性能良好的代码是一项关键技能，因此在这里积累一点经验很值得。

问题

1. 我们从重做本章的测量开始。用 `gettimeofday()` 调用测量程序内的耗时。这个计时器有多准？它能测出的最小时间间隔是多少？先对它的工作机制建立起信心，因为后面的所有问题都要用到它。你也可以研究其他计时器，比如 x86 上通过 `rdtsc` 指令提供的周期计数器。

2. 现在，写一个简单的并发计数器，测量随着线程数量增加，把计数器增加很多次需要多长时间。你使用的系统上有多少个可用 CPU？这个数目对你的测量有影响吗？

3. 接下来，实现一个近似计数器。同样地，测量它在不同线程数和不同阈值下的性能。这些数字与本章看到的一致吗？

4. 按照本章引用的文献 [MS04]，实现一个采用交接锁的链表。你应该先读那篇论文弄懂原理，然后再动手实现，并测量它的性能。交接锁链表在什么情况下比本章所示的标准链表表现更好？

6. 最后，为你钟爱的这个数据结构想一种更有意思的加锁策略，实现它并测量其性能。与直截了当的加锁方案相比，它表现如何？

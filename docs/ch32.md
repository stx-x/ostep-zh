## 32.1 存在哪些类型的缺陷？

第一个、也是最显而易见的问题是：复杂的并发程序里会出现哪些类型的并发缺陷？这个问题很难一概而论，但好在已经有人替我们做完了这项工作。具体来说，我们依据 Lu 等人 [L+08] 的一项研究，该研究细致分析了若干流行的并发应用，以弄清实践中究竟会出现哪些类型的缺陷。

这项研究聚焦于四个重要的大型开源应用：MySQL（流行的数据库管理系统）、Apache（著名的 Web 服务器）、Mozilla（著名的 Web 浏览器）和 OpenOffice（MS Office 套件的免费版本，还真有人在用）。研究者考察了在这些代码库中被发现并修复的并发缺陷，把开发者所做的工作转化成一份定量的缺陷分析；理解这些结果，有助于你了解成熟的代码库里实际会发生哪些类型的问题。

图 32.1 汇总了 Lu 及其同事研究的缺陷。从图中可以看到，缺陷总数为 105 个，其中大多数不是死锁（74 个）；其余 31 个是死锁缺陷。此外还能看到每个应用中被研究的缺陷数量：OpenOffice 只有 8 个并发缺陷，而 Mozilla 有近 60 个。

下面我们更深入地看看这几类缺陷（非死锁、死锁）。对第一类非死锁缺陷，我们用研究中的例子来展开讨论；对第二类死锁缺陷，我们讨论长期以来在预防、避免或处理死锁方面所做的工作。

## 32.2 非死锁缺陷

根据 Lu 的研究，非死锁缺陷占并发缺陷的大多数。可它们究竟是哪些类型的缺陷？如何产生？又该如何修复？下面讨论 Lu 等人发现的两种主要的非死锁缺陷：**原子性违反**（atomicity violation）缺陷和**顺序违反**（order violation）缺陷。

### 原子性违反缺陷

遇到的第一类问题称为**原子性违反**。下面是一个简单的例子，出自 MySQL。在读解释之前，先试着找出缺陷在哪里。动手试试！

```c
Thread 1::
if (thd->proc_info) {
  fputs(thd->proc_info, ...);
}

Thread 2::
thd->proc_info = NULL;
```

<div class="code-cap"><span class="code-label">图 32.2</span>原子性违反（atomicity.c）</div>

在这个例子中，两个不同的线程访问结构 `thd` 中的字段 `proc_info`。第一个线程检查该值是否非 NULL，然后打印它的值；第二个线程把它设为 NULL。显然，如果第一个线程完成了检查、却在调用 `fputs` 之前被中断，第二个线程就可能插进来，把这个指针设为 NULL；等第一个线程恢复运行时，它就会崩溃，因为 `fputs` 解引用了一个 NULL 指针。

按 Lu 等人的说法，原子性违反更正式的定义是这样的：“多个内存访问之间所期望的可串行化被破坏了（也就是说，某段代码本应原子地执行，但执行过程中并没有强制其原子性）。”在上面的例子里，代码对“检查 `proc_info` 是否为非 NULL”与“在 `fputs()` 调用中使用 `proc_info`”之间的关系做了一个原子性假设（用 Lu 的话说）；一旦这个假设不成立，代码就无法按期望工作。

为这类问题找修复办法通常（但不总是）比较直接。你能想到怎么修改上面的代码吗？

在图 32.3 的解法中，我们只是在共享变量的引用周围加上锁，确保无论哪个线程访问 `proc_info` 字段时都持有锁（`proc_info_lock`）。当然，其他访问这个结构的代码也应当在访问之前获取这把锁。

```c

PTHREAD_MUTEX_INITIALIZER;
Thread 1::

if (thd->proc_info) {
fputs(thd->proc_info, ...);
pthread_mutex_unlock(&proc_info_lock);
Thread 2::
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```

### 顺序违反缺陷

Lu 等人发现的另一类常见非死锁缺陷称为**顺序违反**。这里还有一个简单的例子；同样地，看看你能不能找出下面代码中的缺陷。

```c
Thread 1::
void init() {
mThread = PR_CreateThread(mMain, ...);
Thread 2::
void mMain(...) {
mState = mThread->State;
```

<div class="fig-cap-plain"><span class="fig-label">图 32.4</span>顺序缺陷（ordering.c）</div>

你大概已经看出来了：线程 2 的代码似乎假定变量 `mThread` 已经初始化好了（并且不是 NULL）；然而，如果线程 2 一被创建就立即运行，那么它在 `mMain()` 中访问 `mThread` 时，这个值还没被设置，很可能因解引用 NULL 指针而崩溃。注意我们假定 `mThread` 的初值是 NULL；如果不是，情况会更离奇——线程 2 中的解引用会访问到任意的内存位置。

顺序违反更正式的定义如下：“两个（或两组）内存访问之间所期望的顺序被颠倒了（也就是说，A 本应总在 B 之前执行，但执行过程中并没有强制这种顺序）” [L+08]。

### 非死锁缺陷：小结

在 Lu 等人研究的非死锁缺陷中，很大一部分（97%）要么是原子性违反，要么是顺序违反。因此，仔细思考这两类缺陷模式，程序员很可能就能更好地避开它们。此外，随着自动化代码检查工具的发展，它们也应当聚焦于这两类缺陷，因为在部署中发现的非死锁缺陷里，这两类占了这么大的比重。

遗憾的是，并非所有缺陷都像上面那些例子一样容易修。有些需要更深入地理解程序在做什么，或者需要对代码和数据结构做较大规模的重组才能修好。更多细节请阅读 Lu 等人那篇出色（而且好读）的论文。

## 32.3 死锁缺陷

除了上面提到的并发缺陷之外，在许多采用复杂加锁协议的并发系统里，还存在一个经典问题：**死锁**（deadlock）。举例来说，当某线程（比如线程 1）持有锁 L1 并等待另一把锁 L2，而持有 L2 的线程（线程 2）又在等 L1 释放时，死锁就发生了。下面这段代码展示了一种可能出现的死锁：

```c
Thread 1:                Thread 2:
pthread_mutex_lock(L1);  pthread_mutex_lock(L2);
pthread_mutex_lock(L2);  pthread_mutex_lock(L1);
```

注意，这段代码运行起来并不一定会死锁，而只是*可能*死锁。比如，线程 1 先抓到了锁 L1，接着发生上下文切换、切到线程 2；此时线程 2 抓到 L2，并试图获取 L1。于是死锁形成：两个线程各等对方，谁也无法继续。图 32.7 给出了图形化的描绘；图中出现环，就说明存在死锁。

### 死锁为什么会发生？

你也许正在想：像上面这样简单的死锁，看起来很容易避免。比如，只要线程 1 和线程 2 都按相同的顺序去抓锁，死锁就永远不会出现。那么，死锁为什么还是会发生呢？

一个原因在于：在大型代码库中，各组件之间会形成复杂的依赖关系。以操作系统为例。虚拟内存系统为了从磁盘调入一个块，可能需要访问文件系统；而文件系统随后又可能需要一页内存来存放读入的块，于是反过来找虚拟内存系统。因此，大型系统中的加锁策略必须精心设计，以避免代码中自然出现的循环依赖导致死锁。

另一个原因与封装的本性有关。作为软件开发者，我们被教导要隐藏实现细节，从而以模块化的方式让软件更容易构建。遗憾的是，这种模块化与加锁并不那么合拍。正如 Jula 等人指出的 [J+08]，一些看似无害的接口几乎就是在邀请你踩进死锁。例如 Java 的 `Vector` 类和它的 `AddAll()` 方法。这个例程会这样被调用：

```c
Vector v1, v2;
v1.AddAll(v2);
```

在内部，由于该方法需要是多线程安全的，因此既要获取被加入的向量（`v1`）的锁，也要获取参数（`v2`）的锁。这个例程以某种任意的顺序（比如先 `v1` 后 `v2`）获取这两把锁，以便把 `v2` 的内容加到 `v1` 里。如果另一个线程几乎同时调用 `v2.AddAll(v1)`，就有可能死锁——而这一切对调用它的应用来说完全是隐藏的。

### 死锁的条件

死锁的发生需要同时满足四个条件 [C+71]：

- **互斥**（mutual exclusion）：线程对它所需的资源要求排他性的控制（例如线程抓取一把锁）。
- **持有并等待**（hold-and-wait）：线程持有已分配给它的资源（例如已经获取的锁），同时又在等待额外的资源（例如它还想获取的锁）。
- **不可抢占**（no preemption）：资源（例如锁）不能被强行从持有它的线程手中夺走。
- **循环等待**（circular wait）：存在一条线程的循环等待链，链中每个线程都持有链上下一个线程所请求的一个或多个资源（例如锁）。

这四个条件只要有一个不满足，死锁就不可能发生。因此，我们先探讨预防死锁的技术；这些策略各自试图阻止上述某个条件出现，因而都是处理死锁问题的一条途径。

### 预防

#### 循环等待

最实用的预防技术（当然也是被频繁采用的一种）大概是：把加锁代码写成永远不会引起循环等待的形式。最直接的做法，是对锁的获取规定一个全序（total ordering）。例如，系统中只有两把锁（L1 和 L2）时，只要总是先获取 L1、再获取 L2，就能避免死锁。这种严格的顺序保证了不会出现循环等待，也就不会死锁。

当然，更复杂的系统中锁不止两把，因此实现锁的全序可能相当困难（而且也许根本就不必要）。于是，偏序（partial ordering）可以成为组织锁获取、避免死锁的一种有用方式。Linux 内存映射代码里有一个极好的偏序实例 [T+94]（v5.2）；源码顶部的注释列出了十组不同的锁获取顺序，其中既有“先 `i_mutex` 再 `i_mmap_rwsem`”这样简单的，也有“先 `i_mmap_rwsem`，再 `private_lock`，再 `swap_lock`，再 `i_pages` 锁”这样更复杂的。

::: tip 用锁的地址强制加锁顺序

在某些情况下，一个函数必须获取两把（或更多）锁；于是我们知道必须小心，否则就可能死锁。设想一个函数这样被调用：`do_something(mutex_t *m1, mutex_t *m2)`。如果代码总是先抓 `m1` 再抓 `m2`（或者总是先 `m2` 后 `m1`），就可能死锁，因为一个线程可能调用 `do_something(L1, L2)`，而另一个线程可能调用 `do_something(L2, L1)`。要避开这个特定的问题，聪明的程序员可以用每把锁的地址来给加锁顺序定序。只要按地址从高到低（或从低到高）的顺序获取锁，`do_something()` 就能保证无论传入顺序如何，总是以相同的顺序获取锁。代码大致如下：

```c
if (m1 > m2) { // grab in high-to-low address order
pthread_mutex_lock(m1);
pthread_mutex_lock(m2);
} else {
pthread_mutex_lock(m2);
pthread_mutex_lock(m1);
// Code assumes that m1 != m2 (not the same lock)
```

用这个简单的技巧，程序员就能得到一个简单、高效且不会死锁的多锁获取实现。

:::

可以想见，无论是全序还是偏序，都要求精心设计加锁策略，并且必须格外小心地实现。此外，顺序只是一种约定，马虎的程序员很容易无视这套加锁协议，从而可能引发死锁。最后，加锁顺序要求对代码库、以及各个例程如何被调用有深入的理解；只要错一处，就可能招来那个以“D”开头的词¹。

#### 持有并等待

死锁的“持有并等待”这一要求，可以通过一次性地、原子地获取所有锁来避免。实践中可以这样做：

```c
pthread_mutex_lock(prevention);
// begin acquisition
pthread_mutex_lock(L1);
pthread_mutex_lock(L2);
pthread_mutex_unlock(prevention); // end
```

通过先抓取 `prevention` 这把锁，代码保证了在获取锁的过程中不会插入不合时宜的线程切换，于是又避免了一次死锁。当然，这要求任何线程在抓任何锁之前，都先获取这把全局的 `prevention` 锁。比如，若另一个线程想以不同的顺序获取 L1 和 L2，那也没问题，因为它在做这件事时一直持有 `prevention` 锁。

注意，这个解法有几个问题。和前面一样，封装在这里跟我们作对：调用某个例程时，这种做法要求我们确切知道需要持有哪些锁，并提前把它们都拿到手。这种技术还很可能降低并发度，因为所有锁都必须在早期（一次性）获取，而不是在真正需要时才获取。

#### 不可抢占

由于我们通常认为锁一旦被获取就一直保持到调用 unlock 为止，多把锁的获取常常让我们陷入麻烦：在等一把锁的时候，我们还持有另一把。许多线程库提供了更灵活的接口来帮助避开这种局面。具体来说，`pthread_mutex_trylock()` 这个例程要么成功抓取锁（如果可用）并返回成功，要么返回一个错误码表示锁已被持有；在后一种情况下，如果你还想拿到那把锁，可以稍后再试。

这样的接口可以用来构建一个不会死锁、对顺序不敏感的加锁协议：

```c
pthread_mutex_lock(L1);
if (pthread_mutex_trylock(L2) != 0) {
pthread_mutex_unlock(L1);
goto top;
```

注意，另一个线程可以遵循同样的协议、但以相反顺序（先 L2 后 L1）获取锁，程序依然不会死锁。不过，一个新问题随之而来：**活锁**（livelock）。有可能（虽然也许不太可能）两个线程都反复尝试这一序列，又反复失败，谁都拿不到两把锁。此时双方都在不停地重复这段代码（所以不是死锁），但没有任何进展，故而得名活锁。活锁问题也有解决办法：例如，可以在回到循环开头重试之前加一个随机延时，从而降低竞争线程反复互相干扰的概率。

关于这个解法还有一点：它回避了使用 trylock 方案时那些棘手的部分。首先很可能再次出现的问题仍然源于封装：如果其中某把锁藏在被调用的某个例程里，那么跳回开头就变得更难实现。如果代码在途中已经获取了一些资源（L1 之外的），它必须确保也小心地释放它们；比如，如果在获取 L1 之后代码分配了一些内存，那么在获取 L2 失败时，它必须先释放那块内存，再跳回开头重试整个序列。不过，在有限的情形下（例如前面提到的 Java 向量方法），这类做法可以工作得很好。

你可能还注意到，这种做法并没有真正引入抢占（即强行从持有锁的线程手中夺走锁），而是用 trylock 让开发者以一种体面的方式放弃自己对锁的所有权（也就是自己抢占自己）。不过它是一种实用的做法，所以尽管在这点上并不完美，我们还是把它收录于此。

#### 互斥

最后一种预防技术，是干脆消除互斥的需要。总的来说，我们知道这很难，因为我们要运行的代码确实存在临界区。那么能做些什么呢？

Herlihy 有一个想法：可以设计出完全不用锁的各种数据结构 [H91, H93]。这类**无锁**（lock-free，以及相关的无等待 wait-free）方法背后的思路很简单：利用强大的硬件指令，你可以用不需要显式加锁的方式构建数据结构。

举一个简单的例子。假设我们有一条 compare-and-swap 指令——你可能还记得，这是硬件提供的一条原子指令，它做的是下面的事：

```c
int CompareAndSwap(int *address, int expected, int new) {
if (*address == expected) {
*address = new;
return 1; // success
return 0; // failure
```

现在设想我们想用 compare-and-swap 把一个值原子地增加某个量。可以用下面这个简单的函数做到：

```c
void AtomicIncrement(int *value, int amount) {
int old = *value;
} while (CompareAndSwap(value, old, old + amount) == 0);
```

这里我们不再先获取锁、做更新、再释放锁，而是构造了一种反复尝试把值更新为新值、并用 compare-and-swap 完成更新的做法。这样一来，没有获取任何锁，也就不可能死锁（不过活锁仍有可能，所以稳健的解法会比上面这段简单代码更复杂）。

再看一个稍微复杂一点的例子：链表插入。下面是把元素插入链表头部的代码：

```c
void insert(int value) {
node_t *n = malloc(sizeof(node_t));
assert(n != NULL);
n->value = value;
n->next
= head;
```

这段代码完成一次简单的插入，但如果多个线程在“同一时间”调用它，就会出现竞态条件。你能看出为什么吗？（画一张图，想想两次并发插入会对链表造成什么后果——一如既往，假设调度器怀着恶意。）当然，我们可以用加锁和解锁把这段代码包起来解决：

```c
void insert(int value) {
node_t *n = malloc(sizeof(node_t));
assert(n != NULL);
n->value = value;
pthread_mutex_lock(listlock);
// begin critical section
n->next
= head;
pthread_mutex_unlock(listlock); // end critical section
```

在这个解法里，我们按传统方式使用了锁²。换一种思路：让我们只借助 compare-and-swap 指令，以无锁的方式完成这次插入。下面是一种可能的做法：

```c
void insert(int value) {
node_t *n = malloc(sizeof(node_t));
assert(n != NULL);
n->value = value;
n->next = head;
} while (CompareAndSwap(&head, n->next, n) == 0);
```

这段代码把 `next` 指针更新为指向当前的 `head`，然后尝试把新创建的节点换到链表头部的位置。不过，如果在此期间有别的线程成功地换上了新的头节点，这次交换就会失败，本线程于是带着新的头节点值再试一次。

当然，要构建一个有实用价值的链表，远不止插入一项操作；毫不奇怪，以无锁方式构建支持插入、删除和查找的链表并非易事。想了解更多，请阅读关于无锁与无等待同步的大量文献 [H01, H91, H93]。

这类方法有一个著名的例子：Dijkstra 的银行家算法（Banker's Algorithm）[D64]，文献中还描述过许多类似的做法。遗憾的是，它们只在非常有限的环境中才有用，例如在一个嵌入式系统里，你完全清楚必须运行的全部任务集合以及它们各自需要哪些锁。此外，正如上面的第二个例子所示，这类做法会限制并发度。因此，通过调度来避免死锁并不是一种被广泛采用的通用解法。

### 检测与恢复

最后一种总体策略是：允许死锁偶尔发生，然后在检测到死锁之后采取某种行动。例如，如果操作系统一年才死机一次，你直接重启它，然后（愉快地或郁闷地）继续干活就是了。如果死锁很少发生，这种“不解决”的方案其实相当务实。

许多数据库系统采用死锁检测与恢复技术。死锁检测器周期性地运行，构建资源图并检查其中是否有环。一旦出现环（死锁），系统就需要重启。如果还需要先对数据结构做更复杂的修复，则可能要由人来参与，让这个过程容易一些。

关于数据库并发、死锁及相关问题，更多细节可以查阅其他资料 [B+87, K87]。去读读这些著作吧；更好的做法是选一门数据库课程，深入了解这个内容丰富而有趣的题目。

## 32.4 小结

本章研究了并发程序中出现的几类缺陷。第一类是非死锁缺陷，它们出奇地常见，但通常更容易修复。其中包括原子性违反——本应一起执行的一串指令没能一起执行；以及顺序违反——两个线程之间所需的顺序没有被强制。

我们还简要讨论了死锁：它为何发生，以及能怎么办。这个问题与并发本身一样古老，关于它已经写了数百篇论文。实践中最好的办法是小心谨慎、制定一套加锁顺序，从而从一开始就防止死锁发生。无等待方法也很有前景，因为一些无等待数据结构如今正进入常用库和关键系统，包括 Linux。然而，缺乏通用性，加上开发新的无等待数据结构所需的复杂度，很可能会限制这种方法的整体实用性。也许最好的办法是开发新的并发编程模型：在 MapReduce（来自 Google）[GD02] 这样的系统中，程序员可以完全不用任何锁来描述某些类型的并行计算。锁就其本性而言就是麻烦的；也许我们应该尽量避免使用它们，除非真的必须。

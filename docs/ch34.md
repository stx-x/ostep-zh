# 第 34 章　关于并发的总结对话

<div class="chap-en">Summary Dialogue on Concurrency</div>

**教授**：那么，现在你的脑袋是不是有点疼了？

**学生**：（吞下两片布洛芬）嗯，有点。线程可能的交错方式实在太多了，想都想不过来。

**教授**：确实如此。我一直很惊讶：一旦涉及并发执行，区区几行代码也能变得几乎无法理解。

**学生**：我也是！作为计算机科学家，连五行代码都看不明白，挺丢人的。

**教授**：哦，别太难过。你去翻翻最早那批并发算法的论文，有些根本就是错的！而且作者往往就是教授！

**学生**：（倒吸一口气）教授也会……呃……出错？

**教授**：是的，确实如此。不过别告诉任何人——这是我们这行的……

**学生**：我发誓守口如瓶。可如果并发代码这么难想清楚、这么难写对，我们到底该怎么写出正确的并发代码呢？

**教授**：这才是真正的问题，对吧？我觉得可以从几件简单的事做起。第一，保持简单！避免线程之间复杂的交互，用那些广为人知、久经考验的办法来管理线程间的交互。

**学生**：比如简单的加锁，或者一个生产者 / 消费者队列？

**教授**：完全正确！这些都是常见的范式，凭你学到的东西，应该能写出可用的解法。第二，只在绝对必要的时候才用并发；只要能避开就避开。没有什么比过早优化一个程序更糟糕的了。

**学生**：明白了——不需要线程，何必非加不可？

**教授**：正是。第三，如果你真的需要并行，就到其他更简化的形式中去找。比如，编写并行数据分析代码的 Map-Reduce 方法就是个绝佳例子：它实现了并行，却完全不必应付锁、条件变量，以及我们聊过的其他那些讨厌玩意儿所带来的可怕复杂性。

## 关于并发的总结对话

**学生**：Map-Reduce，是吗？听起来挺有意思——我得自己去多读点这方面的资料。

**教授**：很好！你是该这么做。到最后，很多事都得靠你自己去做，因为我们一起学到的东西，只能算是对外面那片知识海洋最粗浅的介绍。读，读，再多读一些！然后动手试一试，写点代码，再多写一些。还要多练；除了这本书，外面还有大量其他资源。就像格拉德威尔在《异类》一书中所说，要想成为真正的专家，你得在某件事上投入大约一万个小时。这可不是全在课堂时间里能做完的！

**学生**：哇，我不知道这话该让人沮丧，还是让人振奋。不过我就当是后者吧，然后开始干活！该去多写点并发代码了……
